# testing-specialist — accumulated knowledge

Read as Step 0 of every testing task; update when you discover a pattern,
find a helper, or are corrected. `testing-specialist.md` holds the durable
rules (DO-WRITE / DO-NOT-WRITE, production→test path map, Mock-vs-Fake).
This file holds **what was learned since**, as principles — never a log.

## How to update this file

- **PRINCIPLES only.** Fold new learning into the matching section as a 1-4
  line rule (merge with an existing bullet if it restates it). A principle
  earns its place only if a future run would act DIFFERENTLY — not "we once
  saw X." Append into the RIGHT SECTION, never onto the end.
- **Raw narrative goes to `testing-specialist.knowledge.archive.md`** under a
  new `## <date> — <title>` heading, then fold the one-line lesson in here.
  A dated "what happened today" entry never belongs in THIS file — that is
  what caused the 2026-07-24 rewrite (432K chars restating ~15 patterns).
- **Budget ~35,000 chars.** Past it, sharpen or retire a principle rather
  than growing the file.

## When to consult the archive

The archive is the full dated history, verbatim and chronological. Grep it
when a principle here is too terse to act on and you need the worked example
(test code, line numbers, failure output); when you hit an unfamiliar
mocktail stub mismatch, `MissingStubError` or fake-vs-real-Firestore
discrepancy not named below; when an emulator-lane setup fails (full
Windows/emulator runbooks live there); when you want a ticket's or area's
full review history (grep the BUT-#### or area name); or when a principle
cites "verified non-vacuous by X" and you want the revert-probe that proved
it, to reuse the technique.

## Principles

### Re-review economics (when asked to re-review "after automated fixes")
- **Confirm the tree actually MOVED before re-reviewing.** Cheapest proof: `ls --time-style=full-iso` the in-scope files against the mtime of the archive entry you last wrote — every file older than it means nothing landed (BUT-1691 round 3, and BUT-1661 rounds 2/3, all reviewed byte-identical trees). Say so up front, then spend the round on a probe the earlier rounds did NOT run rather than re-deriving their findings. **Re-hash the in-scope PRODUCTION files at the END of the round too, not only at the start** — 2026-08-03 (OCR tier 0): the start-of-round hashes matched the previous entry exactly, and then two of the three files moved mid-round, one of them landing a brand-new accept-gate conjunct with no test. A round that only checks motion up front reports on bytes that no longer exist, and the mid-round arrival is the LEAST-tested code in the diff. **The TASK BRIEF is pinned to a hash too, and expires the same way** — 2026-08-05 (`text_layout` round 2, tree moved twice, the second time mid-battery): two of the four behaviours the brief asked me to check (`_mapOf`'s guard, a newline collapse living in `fromJson`) had been DELETED or relocated by the version that landed while battery 1 was running, so answering the brief as written would have reviewed code that no longer existed. Cheapest tell that your own `Read` has expired: a later `sed -n 'A,Bp'` printing different content at the same line numbers. Re-Read, rebuild the mutant list against the new source, discard the battery — and note that a replica driver must print the md5 of BOTH inputs at start, or you cannot date the move afterwards. **Mirror case, cheap to miss: a brief saying "only X changed since your pass" can be anchored to your FIRST closing rather than your REVISED one** (round 4: nothing had moved at all), so diff the brief against the revised hash — and when the hash is unchanged, do NOT re-run the mutants; they were measured on those exact bytes, and the hash is the proof of applicability. **The motion check is also the round's MAP, not just a go/no-go: cross the moved PRODUCTION files against the frozen SUITES.** A production file whose hash moved under a test file that is byte-identical to the last entry's is, by construction, carrying unasserted lines — that one comparison found all three unpinned membership writers in BUT-1797 round 3 before any file was opened twice. **Close every archive entry with the post-fix `md5sum` of each in-scope file** — that makes the next round's motion check one command and beats mtime, which a `cp -p` restore or a formatter touch moves without changing a byte (2026-08-01, BUT-1782 round 3: both files matched round 2's recorded hashes exactly, so nothing had landed; the lib file also read a foreign md5 once mid-round and returned to the recorded hash within minutes — another session, reportable as tree motion, never as a finding). **When the mid-round arrival is a PRODUCTION file whose SUITE did not move, the INDEX version is a free and exact pre-fix mutant: `git show :<path>` into a `test/`-side replica with the class renamed, then run both classes over the new fixtures in one process.** 2026-08-05 (time extractor, which went `A `→`AM` twice mid-round while its suite stayed byte-identical apart from my own addition): worktree/staged answered `null/20`, `null/0`, `null/6939` on the three new assertions and identically on all three controls — proving non-vacuity AND that those tests redden against the current index, i.e. the production file must be re-staged WITH them. Cheaper and safer than mutating `lib/`, and the only probe that measures the exact hazard a partial `git add` creates. Same round, the discrimination tell one level up: **a probe built by RECONSTRUCTING a pattern from a `git diff` you read minutes ago, disagreeing with the live class on one input, is tree motion — not a finding.** The reconstruction carried a since-fixed defect (non-raw Dart literals, so `\s` was silently dropped and `total\s+tid` compiled as `totals+tid`, masked entirely by a sibling alternation answering the same fixture); re-Read the file before writing a word. Dart drops unrecognised string escapes SILENTLY, so any regex built from a non-raw literal is a live hazard worth grepping for.
- The fix loop consumes Critical/High only, so a re-review whose findings are all Low/Medium returns unchanged forever. **Apply zero-risk TEST-ONLY fixes yourself** (fixture swaps, false comments, autopilot duplicates) and file only the production-behaviour items. Never edit production in a review pass — that needs a plan. **"Which of these N new tests is a DUPLICATE" is measurable, not a reading exercise, and the probe is the same replica trick one layer down: copy the ONE EXPRESSION the tests surround (the tier-0 selection `raw == null ? null : (useLayout ? (layoutText ?? providerText) : providerText)` is 3 lines) into a throwaway `_zz_probe_*_test.dart`, write each test's assertions as a named check, and run all of them against every plausible mutant — always-A, always-B, no-fallback, null-when-absent, flag-inverted. A test whose kill-set is a strict SUBSET of another's, THROUGH THE SAME SEAM, is deletable; 2 of 6 were, 2026-08-06. The "through the same seam" clause is the whole safety catch: the no-flag-service-registered test killed a set identical to a deleted one, yet is the ONLY test reaching the real `?? false` lookup (the probe passes the bool directly and cannot model it), so an unqualified subset rule would have deleted the fail-closed arm. Leave a pointer comment where each deletion was, naming the survivor and the measurement, or the next round re-adds it.
- **`git diff <path>` printing NOTHING does NOT mean the file is unmoved: `git status` column 1 `M`/`A` means the other session STAGED, so worktree==index and only `git diff HEAD` shows the change.** 2026-08-05 (BUT-1797 round 4): a scoped file's md5 moved mid-round with an empty `git diff`, which the CRLF principle below would have written off as a line-ending rewrite; `git diff HEAD` showed a real (comment-only) edit. So an md5 move with an empty `git diff` is CRLF *or* staged motion — `git diff HEAD` is the discriminator, and it is also how you spot a brand-new production hunk arriving under a suite you already reviewed. **Cheapest discriminator of all is `wc -l` beside the md5** — 2026-08-05 (`text_layout` round 3): a bare `A ` path whose md5 moved after the final green run turned out to be 379 -> 397 LINES of staged content, not a line-ending rewrite, and `git show :<path> | diff --strip-trailing-cr - <path>` then proved worktree == index. Re-hash AND re-count at the END of every round. **When the parallel session lands a test for the SAME guard you are pinning, delete YOUR copy, not theirs** — theirs is likely already in their report, and duplicated intent is rot whoever authored it; leave a one-line pointer comment where yours was so the next reviewer does not re-add it. A compile error in a fixture parameter you did not write (`permissions:` where the helper takes `members:`) is the usual first sign that you are both in the file.
- Re-verify the archive's claims with a live probe rather than trusting them; a prior round's regex reasoning has been wrong before. **Same for a TWIN-SITE suspicion of your own** — "the sibling normalizer has the same ordering bug" is a hypothesis until you call its PUBLIC api on the two inputs and diff the output. 2026-07-30: `CanonicalPoolKey._strengthenIngredientName` looks like BUT-1739's twin (`leadingNumbersRe` before the approx strip) but is immune, because `_repairOcrDigitsToken` deletes standalone digit tokens a line earlier. A 20-line throwaway test under `test/` (deleted after) beats a source read and stops a false High. **An automated verifier's RED COUNT tells you which SOURCE it ran, not what the tree does — and "N tests are red" is very often the exact signature of the PRE-fix code.** BUT-1739, 2026-07-30: a verifier claimed the reorder never landed and 7 tests were red; the shipped tree runs 24/24, and reverting the two lines produces precisely `+17 -7`. Before believing "the fix is missing", mutate it OUT yourself and compare the red count to the report — a match means the reporter was looking at the old bytes, and that is the finding. **Same when the TASK hands you mutation counts to reproduce: check first whether they were measured on `git diff --cached` bytes while the worktree carries unstaged work on top.** BUT-1772, 2026-07-30: the brief's `2/2/1/1` was measured on the staged 4-test group; the worktree's 5-test group and its fail-closed rewrite give `3/2/1/1`, and the whole fail-closed behaviour the brief describes exists only unstaged. Review the bytes `flutter test` will compile, and say which tree you measured. **The mirror case is commoner and rides on `git status`'s second column: an `MM` path means the very change you were asked to judge may live ONLY in the worktree** (2026-08-03, OCR tier 0: the new `confidence >= _minConfidenceThreshold` conjunct and 247 lines of its tests were unstaged over a pre-fix index). Review and test the worktree, then say plainly that the index does not yet contain it and that all the paths must be staged together — a partial `git add` of the test file alone reddens the very test that pins the fix.
- **The tree can move DURING your round — a Critical is a claim until you re-read the file at the moment you file it.** 2026-07-28: `backfill-shared-list-contributors.ts:160` read `contributorUserIdsMUTANT` on two independent tool calls, then reverted to the correct name 12 minutes later (another session's revert-probe, mid-run). Re-`grep` the exact token and re-`ls --time-style=full-iso` before writing the finding; report a transient artifact as evidence that the SUITE could not see it, not as a live bug. Corollary: back up + `cmp`-restore your own probes in the same Bash call, because a parallel probe on the same file will otherwise be attributed to you.
  **Mirror image — a green suite that reddens ONCE is usually a free revert-probe, not a flake, and you attribute it from the failure VALUE.** Before reaching for flakiness or test-order, list the fixture's ALTERNATIVE sources for the value actually observed: if only the PRE-fix code can produce it, that run compiled pre-fix bytes and has handed you the mutation result. 2026-07-30 (BUT-1736): the menu suite filtered to the new group went `+0 -3` with `Actual: 'Auth Handle'`, then `+3` on the identical command — `'Auth Handle'` exists only in `FakePermissionService`, which the post-fix getter cannot reach, and the `lib/` files were rewritten 11 min after their suites with `.git/index` moving 5 min later. Corroborate with mtimes, then re-run against the final tree with `md5sum` bracketing the invocation before reporting green. **The cheapest instance of this is your OWN new test reddening once at an UNCHANGED lib md5: `flutter test`'s kernel cache is timestamp-keyed, so a suite run seconds after a parallel session rewrites a `lib/` file compiles the PRE-fix bytes.** Discriminate by count before crying flake — `+N -1` where `N` equals every pre-existing test means the single red is the one you just wrote, i.e. you have been handed its mutation proof for free (BUT-1797 round 3, `updateMemberPermissions`). **And note the probe ladder shrank: writing a mutant into a `lib/` file from a Bash heredoc/python call is now REFUSED by the auto-mode classifier and does not execute at all** (check for a missing `.probebak` rather than assuming a partial write) — so it is analytic discrimination (make the fixture's two sources DIFFERENT literals, so a revert cannot coincide with the expected value), then the `test/`-side replica, then mutating the INJECTION. **Cheapest rung, and the only one legal in a READ-ONLY review: a SCRATCHPAD replica run with `C:\tools\flutter\bin\dart.bat --packages=<repo>/.dart_tool/package_config.json <scratch>.dart`** — `package:butlery/...` resolves from outside the tree, so NOTHING in the repo is written, and no parallel session can delete it mid-run (that killed a `test/_zz_probe_*` battery on 2026-08-08). Works for any Flutter-free production file. Copy the function with a `Set<String> off` parameter gating EACH guard, replicate every test's assertions as named checks, and print the whole GUARD x TEST kill matrix in ONE run — 12 guards x 13 tests of `withoutOrphanTail` in ~15 s, against 26 serial `flutter test` runs for the same answer the round before (2026-08-09). **The matrix reframes the question: an unkilled guard is either UNTESTED or UNREACHABLE, and only a reachability sweep separates them** — 4 of those 12 were equivalent mutants masked by an EARLIER gate (`pages.isEmpty`/`last == null` are implied false by `matchesLineCountOf` -> `isComplete`; `textRow == null`/`textRow > rows.length` cannot fire once the row-count gate passed, 252 generated shapes, zero hits). So "add a test" was the wrong finding and "the comment claiming a test pins it is false" was the right one. The matrix names VACUOUS fixtures for free too: a test that needs THREE guards removed before it reddens is not testing the guard its name evokes, and a guard killed by exactly one test is a single point of failure worth a premise assertion. **The replica is the default move on a DIRTY `lib/` file (`git status` shows `M`/`MM`), where `git checkout --` would destroy unstaged work and an Edit-mutant gets the next run refused: copy the source into `test/<same dir>/_zz_probe_mutant.dart` with python, `.replace()` the fix out, rename the class, import it from a throwaway `_zz_probe_test.dart` that PRINTS every value the real tests assert, then `rm` both.** (Driving that loop from python on Windows: `subprocess` cannot exec `flutter` — it is a `.bat`, so `CreateProcess` raises AFTER the driver has printed its input hashes and reads like a mutant failure. Use the absolute `C:\tools\flutter\bin\flutter.bat`, `shell=False`.) Measured 2026-08-03 on `OCRUsageTracker` — one run printed all three pre-fix values (`daily=2` vs 0, `remaining=498` vs 499, two warnings vs none) plus the two deliberately-unchanged controls, so each new test's discrimination and each control's inertness were proved in the same 30 s, with zero risk to the staged tree. Never route around the refusal. **The refusal lands on the TEST RUN, not only on the write, and it is content-sensitive rather than command-sensitive — it now covers `lib/` and `functions/src` alike.** The Edit tool applies a production mutant without complaint, then the next run of that suite is refused: `rating_statistics.dart` (BUT-1781), `account-deletion-cascade.ts` (both `npx ts-node` and `npm run test:*`, minutes after the identical command ran clean), and `list_member_operations.dart` (BUT-1777, 2026-08-01) where a piped AND a bare `flutter test <one suite>` were both refused — so it is the dirty mutant that triggers it, not the shell shape. On a DIRTY production file (no `git checkout --`), budget for "mutant staged, unrunnable": `cp -p` FIRST, restore with the reverse Edit, `cmp`/`md5sum` against the backup, then fall back to a `test/`-side PROBE of the fake's primitive (BUT-1781: what `update()` does on a missing doc) plus analytic discrimination — reading which assertion each scenario's mutant would flip is usually decisive and costs nothing. **When the discrimination rests on a fail-closed CONTROL PAIR (same args, only the stored state differs), first prove the control does not share a mutable seam with what it controls** — BUT-1777: `FakePermissionService.canManageShoppingList` reads its own `_permissions`, which `setShoppingState` never touches, so the refusal is attributable to the new guard and to nothing else; had the state setter also moved the permission fake, both tests would prove zero.
  **And mtime is NOT a "did the tree move" signal when the other session restores with `cp -p`: md5 is.** 2026-07-30 (BUT-1736/1692 round 2): both realtime `lib/` files read as the MUTANT (post-fix doc comment, pre-fix getter, swapped imports → `flutter analyze` gave a hard `non_type_as_type_argument` on `ServiceLocator.get<PermissionService>()`), then read as the FIX two minutes later under an UNCHANGED mtime. **Round 3, same files, same day: the mutant's signature was instead a triad of `unused_import` WARNINGS** (`user_service.dart` unused in both files, `application_provider.dart` unused in the recipe file) — i.e. an import-only mutant analyzes CLEAN of errors and only shows up as dead imports. So the general tell is broader than one error code: **any analyze finding that contradicts the source you just read means re-`md5sum` before writing a word**, and a *set* of files where the flagged imports are exactly the ones the fix ADDED is a revert-probe, never a real defect. Round 3's menu file went `8431cad9`→`35a00654` (pre-fix getter, one line longer) and back inside ~90s while the sibling was `cp -p`-restored (mtime moved 13:52→14:26, md5 identical); the earlier md5-bracketed 52/52 run stayed trustworthy precisely because it was bracketed. Poll md5 in a `for`-loop until it matches the known-fix hash, then re-run analyze bracketed — don't report the contaminated run as a finding. Consequence to know: `flutter test`'s kernel cache is timestamp-keyed, so a timestamp-preserving restore/mutation makes a suite pass against bytes the analyzer says cannot compile (the menu suite ran 24/24 green while its production file held a compile error). Bracket every claim with `md5sum` on BOTH the `lib/` file and the suite, and treat analyze-vs-test disagreement as a cache/tree-motion artifact, not a finding. Both accidental pre-fix runs that round were textbook free revert-probes attributable by VALUE: Dart `+46 -6` with `Actual: 'Auth Handle'`, and the TS suite `18/19` with `rows=0` and NO `logger.warn` line — a shape only `checkRateLimit` + a local throw produces, since a missing `getFirestore()` seam would have printed the swallowed-error warn.
- **When the thing under test is reached through an INJECTABLE SEAM, stage the mutant AS THE SEAM — no production edit needed, and it is the whole probe.** If the seam's type still admits the buggy implementation (the usual case: `enforce?: typeof enforceRateLimit` also admits `checkRateLimit` + a local throw), pass that lambda in a throwaway `__tests__/_zz_probe_*.ts`, run both arms in one process, print both observables, delete the file. 2026-07-30 (BUT-1692): shipped default → `rows=1 code=resource-exhausted`, mutant → `rows=0 code=resource-exhausted` — proving the audit-row assertion is what catches the regression and the thrown-code assertion alone would NOT, which is exactly what the shipped test's docstring claimed. This sidesteps both the "never edit production in a review pass" rule and the auto-mode refusal of `lib/`-writes, and it is strictly better evidence than a source read. Only reach for a real revert when the defect is NOT behind a seam.
- **A CLEAN `lib/` file is the cheapest mutation target — mutate with the Edit tool, restore with `git checkout --`, and expect the md5 to come back DIFFERENT.** `git status --porcelain <path>` empty is your licence: the revert is exact and needs no `cp -p` backup. But `core.autocrlf=true` here, so git normalizes LF↔CRLF when COMPARING (an LF worktree file reads clean) and writes CRLF when CHECKING OUT — so a post-restore md5 mismatch is a line-ending rewrite, not tree motion, and git still reports the file clean. Verify with `git status`/`git diff --stat` on the path, not md5, after a checkout-restore. Measured 2026-07-30 on `shopping_repository_query_module.dart`: `be3790d7`→`a898b23c`, git clean, CRLF matching every sibling.
- **For any "would the RULES allow this?" question, the emulator settles it in ONE run and you do not need a plan to ask.** `firebase-tools` + Java are installed here, `@firebase/rules-unit-testing` is already a functions dep, and a throwaway `functions/src/__tests__/_zz_probe_*.ts` run under `cd functions && npx firebase emulators:exec --only firestore --project demo-test "npx ts-node src/__tests__/_zz_probe_x.ts"` prints allow/deny per arm in ~90 s. The denial message names the RULE LINE and the cause (`evaluation error at L724 … Null value error`), which is stronger evidence than any source read, and it costs nothing to add a control arm (same read, doc now present) so a wiring failure cannot masquerade as a denial. Delete the probe in the same call. Use it before filing any Critical that rests on rules semantics — a client-side read/write a fake happily serves is otherwise unfalsifiable from Dart.
- **A MEASUREMENT quoted in a comment is verifiable in one command whenever a shipped tool prints it — run the arm, never cross-read the files that quote each other.** 2026-08-08 (BUT-1816 round 6): `dart run tools/corpus_split_eval.dart --edge-crop` (~40 s, no network, corpus at `../butlery-corpus`, dart is `C:\tools\flutter\bin\dart.bat`) reproduced every figure in `edge_crop.dart`, the mlkit adapter, the flag comment and the test fake — 132/181 cropped pages, 496 rows, blind spot 62 = 37 + 25, precision 66.26 -> 66.64, band 45 pages 66.65 -> 67.70, recall 91.56 -> 91.54. Three files agreeing proves only that one was copied from the others; the tool is the only witness. Corollary for reviewing such comments: a figure quoted WITHOUT the caveat its source doc insists on (here "the recall pair is an upper bound") is an advisory, not a false claim — say which.
- **READ THE MUTATED LINE BACK before believing a mutant's red count.** Patching a Dart file from a shell heredoc mangles backslashes silently: reverting `SwedishWordBoundary.boundedRegExp` to `'\\b(...)\\b'` wrote `'\b(...)\b'` — a literal U+0008, not a boundary — and the "reverting reddens exactly four" claim read as FALSE at 15 reds (2026-07-27). A mutant that reddens far MORE than the comment claims is the tell that you built the wrong mutant, not that the comment is wrong. `sed -n` the line, then re-run.

### Project-specific test infrastructure (full detail in `testing-specialist.md`)
- Production ServiceLocator bridge: `production.ServiceLocator.initialize(DIContainer())` in `setUpAll`. Two ServiceLocator classes (production wraps DIContainer, test uses GetIt directly) share the same `GetIt.instance`.
- `MockUnifiedRecipeService.setRecipeState()` defaults `isInitialized: false` — always pass it explicitly.
- Debounced VM methods need `fakeAsync` + `async.elapse(Duration(milliseconds:300))`. `executeDebounced` triggers 3 notifications: setLoading(true) + operation + setSuccess().
- Per-view "mechanical" tests were deleted (BUT-387 Phase 6) — `test/views/` is journey-test territory only (owned by `e2e-test-specialist`); heavy-scaffolding views get ONE beat in a journey test, not a standalone widget test.
- **A repoint to `collectionGroup(...)` is HALF a fix, and the other half is a declaration test.** Automatic single-field indexes are COLLECTION-scoped, so a collection-group query filtered on a field needs a `fieldOverride` with `queryScope: COLLECTION_GROUP` in `firestore.indexes.json` or it FAILED_PRECONDITIONs on every invocation — and `firebase deploy --force` prunes anything absent from that file. Pin it with a plain-Node assertion suite over the JSON (template: `functions/src/__tests__/recipe-collection-group-indexes.test.ts`, BUT-1781; sibling precedents `firestore-ttl-policies.test.ts`, `compute-feature-retention.test.ts`). Three arms, all needed: the override exists at group scope; the EXACT SET of overrides for that collectionGroup (a count alone stays green on a delete+add swap); and the querying source still spells the field — anchored on `.where("core.x"`, never `src.includes("core.x")`, which every docstring satisfies. Add the old wrong path as a regression arm (`!/\.collection\(\s*"recipes"\s*\)/`). Verified non-vacuous by copying the suite to a `_zz_probe_*` and drifting one fieldPath: 4 of 12 redden. **Register the npm script in the same edit** — `functions/scripts/run-all-tests.js` auto-discovers `test:*` from package.json, so an unregistered suite is an orphan nothing runs (`npm run test:script-test-registration` is the guard; its "the real repository passes its own guard" case is the one to read).
- **Any SOURCE-TEXT assertion suite must strip comments before matching, and its non-vacuity probe is a string mutant, never a file mutant.** The settings these suites pin (`retry: true`, `timeoutSeconds: X`) are the ones a careful author EXPLAINS in prose right beside the code, so a bare `src.includes("retry: true")` stays green after the real setting is deleted — measured on `cascade-retry-semantics.test.ts` (BUT-1781), whose first version reported 11/11 with the setting removed. Strip with `/\/\*[\s\S]*?\*\//g` then `/(^|[^:])\/\/.*$/gm` (the `[^:]` keeps `https://` intact). Probe it without touching `functions/src` at all: read the real file, `.replace()` the setting out of the STRING, and print base-vs-mutant for each regex from a throwaway `_zz_probe_*.ts` — 6/6 flipped there, and it sidesteps the auto-mode refusal that a production mutant triggers.
- **A mocktail matcher does NOT go vacuous merely because the production call gained a named argument — it goes vacuous when that argument's value stops equalling the parameter's DEFAULT.** 2026-08-07 (`autoParseMulti(text, layout:)`, measured in a throwaway probe against the real `MockImportManager`): Dart's noSuchMethod forwarding fills every OMITTED named parameter into the Invocation with its default, so a bare `f(any())` still matches a real call carrying `layout: null` (`verifyNever` correctly reddened, "Unexpected calls"), and only stops matching once the value is non-null. Consequence for review: repairing such a `verifyNever` to `layout: any(named: 'layout')` is right and strictly stronger — prove it with a 4-arm probe (null arm matches / non-null arm matches / bare-matcher mutant / `verifyNever` control that must THROW), never by reading mocktail's source. And when a comment explains the repair as "mocktail matches on the key set", correct it: the key set is always complete on both sides.
- **A poll-until-condition loop is discriminating only if the ASSERTION sits after it, and the cheap proof is a replica with the trigger removed, not a `lib/` mutant.** 2026-08-07 (photo-import draft discard, `clearPhoto` -> unawaited discard): copying the test into `_zz_probe_*` and deleting the `vm.clearPhoto()` line reddened at exactly the 5 s ceiling with `Expected: null / Actual: PhotoImportDraft` — so the bound only forgives a SLOW discard, never a missing one. Poll the LAST observable step of a multi-step async teardown (prefs), not an intermediate one (the staged file), or the tail stays unbounded. A `Stopwatch` ceiling is the shape `scripts/check_test_real_time.sh` allows; its `DateTime.now()` rule matches TEXTUALLY (comments included) and its delay rule only fires on `Future.delayed(Duration(seconds|minutes|hours:` — a 10 ms poll interval is clean.
- **A `retry: true` adoption owes a REACHABILITY read of its own bound.** v2 event triggers default retry OFF, so `throw` is logged and dropped; turning it on buys 7 days of redelivery, which is why these ship with an `isCascadeEventExpired(event.time)` age guard. Check where that guard SITS: both BUT-1781 cascades deref `event.data!.before.data()` above it, so any throw from that line escapes the bound entirely — i.e. the one failure mode the guard exists for. `event.time` is the right field (preserved across redeliveries); the guard must be the handler's FIRST statement.

### Coverage decisions
Codecov: 60% project / 70% new patches / 2% drop tolerance — floors, not targets; one behaviorally meaningful test beats ten getter checks. Project floor DECIDED at 55% (2026-07-11) — don't file generic "raise coverage" tickets.

### Conscious-skip taxonomy (each discriminant is distinct)
- Static-method orchestrator: skip only when ALL hold — ≤3 calls, no injection seam, each in its own try/catch, no branching beyond the catches.
- Static disclosure whose sync contract is compiler-enforced (renamed `AnalyticsEvents.*`/l10n constant fails analyze/gen-l10n before any test runs).
- Pure-nav affordance (`pushNamed(<const route>)`) — route constant is compile-checked.
- Nth surface adopting an already-proven predicate: prove via `git diff --staged --name-only` — no new surface if the pure-logic file is absent from the diff.
- Mechanical `AppColors→theme` swap: skip only if finder-level assertions are unaffected.
- `SemanticsService.announce` in a fire-and-forget handler is skippable UNTIL the view gains a DI seam or full-shell harness — a conscious skip is dated, not permanent.
- A "sole guard"/"bypass not possible" comment is a claim until a test actually enters that exact branch. **Same for a KNOWN-GAPS / "read this before quoting the number" doc block shipped WITH a data-path fix — no test can ever catch a false comment, so verify each listed gap against the model's SERIALIZER, and never treat `firestore.rules` declaring a subcollection or a deletion cascade sweeping it defensively as evidence the client writes it.** Measured 2026-07-30 (BUT-1724, `compute-feature-retention.ts`): `UnifiedShoppingList.toFirestore` embeds `items` as an ARRAY and every mutation helper routes through `copyWith(updatedAt: clock.now())`, so the new comment's "personal-list item ticks are under-counted because items live in an `items` subcollection" is false in the direction of UNDER-selling the metric, and it prescribes a costly non-fix ("bump the parent on every item write") that IS already the behaviour — `account-deletion-cascade.ts:494` states the opposite in the same repo. - A comment-only diff owes no new test IF the claim is already pinned by a spy/Fake that would fail-loud if false — verify, don't trust.
- **A rationale that cites a BACKEND PROPAGATOR or DELETION CASCADE as covering a field is two greps, and both usually fail.** Resolve the collection CONSTANT, not the prose name (`Collections.sharedRecipes` = `"shared_recipes"`, NOT `shared_content`), then grep the cascade's query field. ### Vacuity patterns — the recurring ways a "passing" test proves nothing
The single most repeated finding across two months of review. Check every new test against this list.
- **Inverse case, and a reviewer's own failure mode: a fixture sitting EXACTLY on a threshold is usually the only thing pinning `>` vs `>=` — never suggest "add slack" without executing the comparison.** BUT-1816 round 4, 2026-08-08: `edge_crop`'s one-third cap is `bleed.length > lines.length * (1/3)`; `12 * (1/3)` is EXACTLY `4.0` in IEEE754 (the true product `4 - 2^-52` ties between `4 - 2^-51` and `4.0`, ties-to-even picks `4.0`), so a 4-of-12 crop-happens fixture plus a 6-of-12 crop-refused one kills the `>=` mutant, and the slack I offered would have deleted that kill for nothing. Float boundaries are an EXECUTION question (a 5-line `dart run` probe), never a reading one — and the same probe is how you confirm a "clears the cap with slack" comment (2-of-7 = `2 > 2.333` false) instead of trusting the arithmetic in the comment.
- **An enum-driven `defaults()` factory owes a KEY-SET-COMPLETENESS test, and per-key spot checks can never substitute.** A member the hand-written literal forgets is not "off by default": every reader takes it through `orFalse()`/`safeBool`, which answer a missing key `false`, so the whole notification/feature class is dead for every new user AND for every corrupt-cache fallback that returns `defaults()`. Pin `expect(p.categorySettings.keys.toSet(), NotificationCategory.values.toSet())` — not circular, because the two sides come from independent sources (the factory literal vs the enum declaration), and `equals` on a `Set` really does discriminate a missing member (probed 2026-08-01, BUT-1782: removing one member reddens with "does not contain"). Same read on any multi-clause guard: check whether a LATER clause already rejects everything an earlier one does — `SerializationUtils.hasRequiredFields` (containsKey && `!= null`) is strictly SUBSUMED by a following `data['x'] is! Map`, so an earlier round's claim that deleting it reddens the `'{}'` test was false, and only the `is! Map` clauses are load-bearing.
- **Circular determinism.** Calling the same pure function twice, or deriving the expected value from the SAME const the test guards, proves referential transparency, not the invariant. Pin the literal OUTPUT VALUE (`expect(buildId('r1','m1'), 'r1_m1')`, not `expect(buildId(...), buildId(...))`). ### Disposal & lifecycle guard idioms (BaseViewModel family)
- `BaseViewModel` already guards disposal TWICE (`clearError()` and `notifyListeners()`), so a subclass's OWN third guard is usually untestable-to-fail — `dispose()→clearError()→returnsNormally+notified==0` can't go red from removing it. Only test a disposal guard protecting an OBSERVABLE effect no base guard blocks (e.g. a late stream emission mutating a private field BEFORE the guarded notify — assert the STATE stays unchanged).
- Two quadrants when sweeping a guard across many VMs: (A) delegate disposed BY this VM's own `dispose()` — test `returnsNormally`+`notified==0`. (B) delegate is a SHARED SERVICE outliving the VM — `returnsNormally` is VACUOUS; assert the service's error SURVIVES the VM's disposal instead.
- A class with BOTH a local `_isDisposed` (set at the START of its own dispose) and inherited `BaseViewModel.isDisposed` (flips only inside `super.dispose()`, often LAST) must have any new guard use the SAME flag its own callbacks use. Migrating `ChangeNotifier`→`BaseViewModel` turns the old `throwsFlutterError` post-dispose-notify test into `returnsNormally` — also assert the listener was NOT invoked, or it can't tell "no-op" from "leaked".
- A VM shadowing `error`/`hasError` must be proven by driving a FAILED base `executeAsync` (populates `super._error`) — seeding only a service-level error while base stays clean can't catch a dropped override. First check the VM calls base `executeAsync` at all; if error routing is fully manual, `super._error` is dead and this pattern doesn't apply.
- `executeAsync` RETHROWS on failure (not null). Prove it indirectly via a caller that only retries on THROW (assert attempt count) — a bare try/catch around the call is vacuous re: rethrow-vs-null.
- **A `dispose()` that clears DATA (not just controllers/timers) creates a use-after-dispose window for any long-running op still holding the object** — read the collaborator's dispose body before trusting "just a leak fix" (`FormFieldsManager.dispose()` also does `_values.clear()`). Test: dispose mid-operation (after the op's last await point), assert the WRITE still carries the user's data. Check whether the op's own `if (_disposed)` guards are even live — a manager the owner never disposes has permanently-false guards.
- **A "disposes its children" test asserting only `returnsNormally` on a still-callable method is vacuous.** Materialize the child (e.g. `state.manager.controllers`) BEFORE dispose, then assert it is dead: `expect(() => controllers.first.addListener(() {}), throwsFlutterError)` — `ChangeNotifier.addListener` debug-asserts not-disposed, so the assertion flips when the dispose line is reverted.
- **A new throw-on-disposed guard inside a shared builder is only safe at callers that catch.** It converts silent corruption into an uncaught exception everywhere else — enumerate call sites yourself; a comment claiming "every caller sits inside a safeExecute" is a claim, not a fact (BUT-1667: `RecipeFormState.createRecipe`'s unguarded `RecipeFormCoordinator.syncToCollaborative` caller was only guarded on the third pass, and never got a test — `RecipeFormCoordinator` has no test file at all). ### Contract pinning: selectors, ordering, equality, revert

### Settings-hydration & sentinel-parameter template (recurring: BUT-1220, 674, 1322, 1610)
Any field persisted via a private settings sub-doc needs: (1) a hydration test seeding the sub-doc DIRECTLY; (2) a corrupt-value test that ALSO asserts a SIBLING merged field survives (the merge is one `copyWith` in one try/catch — a naive parse of the corrupt field can abort the WHOLE merge, invisible if you only check the corrupt field's own null-safety); (3) a save-path test asserting the settings doc has it AND the public doc does NOT (privacy-leak guard) + round trip; (4) if the field has 3 serialization surfaces (Firestore/JSON-cache/copyWith), each needs its OWN test.
Sentinel-parameter contracts (`Object? field = _unset`) need both quadrants at the layer where omission is possible: omit→preserved, explicit-null→cleared. Prefer capturing the forwarded ARGUMENT IDENTITY against the sentinel (`identical(captured, Sentinel)`) over a downstream no-op — a regressed VM forwarding an in-memory null instead of the sentinel can coincidentally suppress the same effect.

### One-off gotchas, Windows/runner notes, and the revert-probe technique
- `Semantics(label:)` wrapping a tooltip'd button MERGES into one node with a concatenated label — match with `RegExp` (never exact String), bracket `bySemanticsLabel` with `tester.ensureSemantics()`/`handle.dispose()` in the SAME test.
- Optional-override params with an l10n `??` default: assert an injected override renders AND `find.textContaining(<default's unique substring>)` findsNothing — a shared substring makes the default-path test blind to whether the override threads through.
- A `GlobalKey` preventing State recreation is tested behaviorally: drive the state-changing event that WOULD recreate it, assert continuity survives — never assert on the key itself.
- **"Derives from a scaled/filtered list" claims need the list to provably DIFFER from its source** (factor ≠ 1.0) — testing at the default/identity config is structural blindness.
- A copy-SPLIT (two strings sharing a suffix) needs an assertion on the substring UNIQUE to each.
- Real `.xlsx` stores text via shared-strings (`t="s"`), not `inlineStr`.
- Age-boundary tests must pin the exact legal threshold on BOTH sides, not just far-side values.
- `export 'stub' if (dart.library.js_interop)` services: test only the stub's no-op contract; the web state machine is unreachable from VM tests.
- **When the test under scrutiny reads a FILE PATH rather than calling code (registry/structural lints, declared-index-config asserts), the mutant is a GIT REVISION — no `lib/` edit, no replica of production, nothing to restore.** `git show HEAD:<path> > scratch/`, then a throwaway replica of the *test's own* parse/walk parameterised on the path, run twice: control against the live file, mutant against the extracted revision. This is the cheapest probe in the ladder and the only one available when the "fix" is a deletion (there is no code left to mutate). Assert the mutant's exact expected set, not just non-emptiness — that is what distinguishes "the lint fires on this" from "the lint fires on something."
- **A GENERATED file in a diff (`lib/l10n/app_localizations*.dart`) is verified by re-running its generator, not by reading it.** `cp -r lib/l10n` to scratch, `flutter gen-l10n`, byte-compare: identical bytes means genuine generator output in sync with both `.arb` files and no hand-edit, and it needs no restore. **The load-bearing step is the mtime check** (`ls --time-style=full-iso`) — a byte-comparison alone proves nothing if the generator silently skipped the files; the three `.dart` outputs must show the run's timestamp while the `.arb` inputs stay untouched. Verified 2026-07-30 on the `shoppingListChangedElsewhere` key. Note these outputs are CRLF on Windows while the `.arb` sources are LF, so compare in BINARY and don't read the difference as drift.
- **A DELETION mutant on a line inside a fluent chain does not compile — substitute an always-true equivalent instead.** Dropping a `.where(...)` from `firestore.collection(x).where(y)` runs the next argument into the collection ref, and the resulting `loading … [E]` reads as "everything reddened", which is the tell for a broken mutant, not a strong test. Replace the predicate with one every fixture satisfies (`.where('name', isNull: false)`) — same "the probe lost its scoping" semantics, valid syntax, and the failure prints the extra ids so the direction is readable. For a multi-probe query file, seed a FOURTH "stranger" doc no probe should match and add a PARTITION test over the union of all probes: each per-probe test then owns a negative half, and any probe widening into a sibling's territory reddens twice (verified BUT-1732, 2026-07-30 — 8 mutants, 4 of them reddening exactly one test each, which is the artefact proving the guard/cap/predicate tests aren't piggy-backing on one fixture). **Re-measured on the two `memberPermissions.$uid` membership filters (BUT-1746, 2026-07-30): substituting `.where('name', isNull: false)` reddens exactly 4 — the positive AND the "member of nothing" negative at BOTH `readAll` and `collaborativeListsStream`. That is what upgrades such a suite from "pins the SPELLING" to "pins the SCOPING": a spelling-only revert to `isNotEqualTo: null` reddens only the positives, because the fake throws `Unsupported` and `readAll` catches into `[]`, so the negatives pass for the wrong reason (their own comment should say so).**
- **Revert-probe (the reliable non-vacuity proof):** copy the production file to scratch, string-replace the fix OUT, run the affected suite, confirm EXACTLY the expected test(s) go red at a unique assertion, restore and byte-verify with `cmp`. Construct the REAL object under the exact constructor wiring the bug lived in. Batch probes in one run only when each fails uniquely; separate when they share a code path. Back up IMMEDIATELY before editing — a parallel session may be editing the same file.
  **Three mechanics that make this survive a live parallel session (18 probes, 2026-07-28).** (a) Do the whole cycle — `cp` to `.bak`, mutate, run, restore from `.bak`, `cmp` — in ONE Bash call, and drive it from a tiny reusable script (`apply <file> <tag> <old.txt> <new.txt>` / `restore <file> <tag>`) that reads the OLD/NEW text from FILES; that is the only way a Dart snippet with backslashes survives the shell (a bash heredoc halved `\\s`→`\s` in the same session, and the Python `SyntaxWarning: invalid escape sequence` was the only tell). Assert the search text occurs exactly ONCE before writing. (b) On Windows, read/replace/WRITE IN BINARY. Python text mode silently rewrites CRLF→LF, so the md5 no longer matches the pristine file even though `git diff` still reads clean (autocrlf normalises) — a "restored" claim backed only by `git diff` is not byte-exact. (c) A mutated token that is MISSING at the end of the round is not automatically a failed restore: on this round `isBareGlutenHeadingCandidate` had been refactored away by the other session between the probe and the audit. Distinguish by `ls --time-style=full-iso` mtime + `git diff` of the region, never by assumption, and re-run the affected suites against the FINAL tree before reporting green.
- **When you are told not to touch `lib/` (or the plan-threshold gate refuses the edit), do NOT route around it.** Use a FAITHFUL REPLICA probe instead: copy the method body into a throwaway `test/zz_scratch_*_test.dart` (test files aren't gated) with the one line under probe swapped for a `Function` parameter, and open with a CONTROL test asserting the unmutated replica agrees with the real production function on every fixture — without that control the replica proves nothing. **This scales to a WHOLE CLASS** (used for BUT-1669/1667, 2026-07-26): `cp lib/X.dart test/.../zz_scratch_x_replica.dart`, rename only the class + its constructor, then `cp` the real suite beside it and sed the one import + the type name. Every `package:butlery/...` import resolves unchanged from `test/`, so the replica is byte-faithful; run the copied suite once UNMUTATED as the control (55/55 green proved the VM replica faithful), then mutate. It is blocked only when a mixin declares the type (`RecipeBackwardCompatibilityMixin` requires `RecipePersistenceManager get persistenceManager`, so a renamed replica can't be swapped in one layer down). Delete the scratch pair and re-grep the production file for the mutated token afterwards. Then run each mutant and print which fixtures flip. This also probes mutants the ticket didn't ask for (each HALF of a two-sided lookaround) in the same run, which a real file edit makes tedious. Delete the scratch files and `md5sum` the production files against the backups in the same call as the cleanup.
- **Cheapest probe of all when the SUT already injects the collaborator: mutate the INJECTION, not `lib/`.** If the bug is "the mutator built on X instead of Y", a throwaway harness that feeds the mutator X through the existing constructor seam reproduces the buggy output exactly, with the REAL production method bodies running. No lib/ edit, no replica, no control test needed (the bodies are genuine). Used 2026-07-26 to drive all six `ShoppingItemOperationsModule` collaborative tests red in one run. Applies whenever the differing value arrives as a constructor callback's argument.
- **A one-character change inside a string literal cannot be reviewed from `git diff` — `od -c` the BEFORE side, or you will invent the bug.** Live trap, `firebase_weekly_menu_plan_repository.dart` (2026-07-17, twice on 2026-07-26, and BUT-1690): the doc-ID prefix ranges read as `isLessThan: '${userId}_'` on BOTH sides of the diff — the classic empty range on a GDPR-export and a cascade-delete method — because HEAD already held a LITERAL U+F8FF (bytes `357 243 277`); the diff only escapes it. Behaviourally a no-op every time, so the finding is a FALSE one. Habits, in order: `od -c` / `git show HEAD:` any one-char literal diff before reasoning; **grep the ARCHIVE for the FILE NAME whenever a diff surprises you**; and never trust `grep uf8ff`, which measures NOTATION not semantics (it finds the sentinel only where escaped, reading as a one-of-N-siblings bug — the exact wrong conclusion). **The byte-form grep FALSE-NEGATIVES silently too**: `grep -P '\xef\xa3\xbf'` matches CHARACTERS under a UTF-8 locale and reported `functions/src` clean while `cat -A` showed the literal on a live GDPR-cascade bound; `LC_ALL=C grep -P` is refused outright here. Only three things work — the CODEPOINT form `grep -nP '\x{F8FF}'`, a Python sweep against `chr(0xF8FF)`, and `cat -A` (`M-oM-#M-?`). **And the char survives being TYPED as an escape into a tool call** — writing the six-char escape into Write/Edit/a heredoc produced the raw character twice in one session, which then broke a later `Edit`'s own `old_string`. Write `chr(0xF8FF)` / `U+F8FF` in prose only, then grep your own artefact.
- **Write throwaway probes with the Write tool, never a bash heredoc, and use RAW Dart strings (`r'\bfoo\b'`).** Backslashes silently die crossing the Bash layer even inside a quoted `<<'EOF'`: `RegExp('\\b$w\\b')` arrived as pattern `socker` with both boundaries GONE, so a probe reported "the old regex never matched" for every fixture and would have had me file a false finding against correct test comments. Always `print(re.pattern)` in a regex probe and eyeball it before trusting a single result.
- **A new grep guard in `lefthook.yml` is not a CI control, and its path handling needs one probe.** lefthook renders `{staged_files}` as REPO-RELATIVE paths (verified with `npx lefthook run pre-commit --command <name> --file <p> --force -v`, which prints `files after escaping: lib/...`), so a guard whose comment-skip filter anchors past a `path:line:` prefix is safe under the hook — and false-FAILS on a manually passed Windows absolute path, because `C:/…` splits at the drive colon and every WHY-comment naming the banned spelling is then reported (reproduced on `tools/check_null_filter.sh`, 2026-07-30). Anchor on the LAST `:<digits>:`. Separately: this repo's repo-wide grep guards run in `.github/workflows/architecture-validation.yml` (8 of them); a guard wired ONLY pre-commit is bypassed by `LEFTHOOK_EXCLUDE`, a checkout without `lefthook install`, and any merge — so grep the workflows before crediting a guard as a control, even when the script already supports an arg-less whole-repo mode.
- A `TimeoutException ... during "loading"` with 0 tests run is compile-bound (~12min shared `lib/` compile), not a hung test — split the invocation per-file to confirm.
- **Never pipe a mutation driver into `head` — SIGPIPE kills it before its cleanup, and its own "probe files removed" line is then a lie you never see.** 2026-08-05: `python mutate.py | head -14` left `_zz_probe_impl.dart` + `_zz_probe_test.dart` in `test/`, which `flutter test <dir>` would have run and a `git add` would have staged. Pipe to `tail`, redirect to a file, or re-run whole; and close every probe round with `git status --porcelain` on the directory, never with the driver's own claim.

### Firestore-rules `.ts` suites (emulator-gated)
- Every `&&` clause in an `allow` rule gets a failing test; every `cannotModify`/`hasRequiredFields` list needs a test PER FIELD.
- A failure-only update suite can be silently over-restrictive — pair denials with an `assertSucceeds` on a mutable field.
- The emulator persists docs ACROSS invocations — suffix create-test ids with a per-run `RUN = Date.now().toString(36)`, or a fixed-id create silently becomes an update on the 2nd run.
- These are hand-rolled `npx ts-node` runners against `127.0.0.1:8080` — time out without `firebase emulators:start --only firestore` running first. `functions/tsconfig.json` is `include: ["src"]`, so `npx tsc --noEmit` in `functions/` DOES typecheck `src/__tests__` under `strict` — a free non-emulator check on a rules suite you cannot run.
- **A client-side filter test on `FakeFirebaseFirestore` says NOTHING about whether the server accepts that query — the fake evaluates no rules — and a single-doc `get()` deny test cannot see the query branch either, because rules are not filters: the engine refuses a whole QUERY when any candidate doc fails the read rule.** So a membership-filtered collection read owes THREE rules assertions beside the Dart ones (BUT-1746 shape, added 2026-07-30): filtered-ALLOW using the SDK's own spelling (`isNull: false` compiles to `where(f,'!=',null)`) plus a non-empty premise check so it can't pass vacuously; unfiltered-DENY whose ONLY delta is the missing `where()`, with one foreign doc seeded so there is something to refuse; and filtered-ALLOW-but-empty for a member of nothing, proving the fixed shape is safe for every actor rather than an error screen. Pick an actor no other test ever seats as owner/member — the emulator persists, so reusing the "stranger" uid makes the empty-result assertion flake.
