# testing-specialist — accumulated knowledge

Read as Step 0 of every testing task; update when you discover a pattern,
find a helper, or are corrected. `testing-specialist.md` holds the durable
rules (DO-WRITE / DO-NOT-WRITE, production→test path map, Mock-vs-Fake).
This file holds **what was learned since**, as principles — never a log.

## How to update this file

- **PRINCIPLES only.** Fold new learning into the matching section as a 1-4
  line rule (merge with an existing bullet if it restates it). A principle
  earns its place only if a future run would act DIFFERENTLY — not "we once
  saw X." Append into the RIGHT SECTION, never onto the end.
- **Raw narrative goes to `testing-specialist.knowledge.archive.md`** under a
  new `## <date> — <title>` heading, then fold the one-line lesson in here.
  A dated "what happened today" entry never belongs in THIS file — that is
  what caused the 2026-07-24 rewrite (432K chars restating ~15 patterns).
- **Budget ~35,000 chars.** Past it, sharpen or retire a principle rather
  than growing the file.

## When to consult the archive

The archive is the full dated history, verbatim and chronological. Grep it
when a principle here is too terse to act on and you need the worked example
(test code, line numbers, failure output); when you hit an unfamiliar
mocktail stub mismatch, `MissingStubError` or fake-vs-real-Firestore
discrepancy not named below; when an emulator-lane setup fails (full

full review history (grep the BUT-#### or area name); or when a principle
cites "verified non-vacuous by X" and you want the revert-probe that proved

## Principles

### Re-review economics (when asked to re-review "after automated fixes")
- **Confirm the tree actually MOVED before re-reviewing** (`git diff` + test count vs the archive's last entry). BUT-1661 rounds two and three both reviewed a byte-identical tree.
- The fix loop consumes Critical/High only, so a re-review whose findings are all Low/Medium returns unchanged forever. **Apply zero-risk TEST-ONLY fixes yourself** (fixture swaps, false comments, autopilot duplicates) and file only the production-behaviour items. Never edit production in a review pass — that needs a plan.
- Re-verify the archive's claims with a live probe rather than trusting them; a prior round's regex reasoning has been wrong before.

### FakeFirebaseFirestore vs emulator decision tree
| Behaviour under test | Use |
|---|---|
| Plain reads/writes/queries, `collectionGroup`+equality, `orderBy` on a present field | `FakeFirebaseFirestore()` in `setUp` |
| `FieldValue.increment`, `serverTimestamp` (usually), transactional writes, security rules | Emulator lane, or `firestore-rules-tester` |
| `GetOptions.source` (cache-first vs server) | NOT testable on the fake — ignores `source`, returns the same doc either way. Worse, real Firestore THROWS `FirebaseException(code:'unavailable')` on a `Source.cache` MISS; it does not return `exists:false`. So any `if (!cached.exists) throw NotFound` branch under a cache read is DEAD in production and its "passing" test is a fake artefact. Assert the outcome contract only. |
| Service that wraps Firestore | Mock at the repository interface |
- **`FakeFirebaseFirestore.runTransaction` is a NO-OP PASSTHROUGH — it can never prove atomicity.** Read the source (`fake_cloud_firestore_instance.dart:113` + `_DummyTransaction:210`): it builds a dummy, calls the handler once, and returns. `transaction.get` is a plain `docRef.get()`; `transaction.set/update/delete` write IMMEDIATELY and **drop `SetOptions`** (so `merge:true` is unverifiable — a sibling field the real merge preserves is wiped on the fake); `timeout` and `maxAttempts` are ignored; there is no isolation, no abort, no retry. Consequences, all verified 2026-07-26: (1) deleting `runTransaction` from production and doing a bare read-modify-write leaves such a suite 100% green — always run that mutation before crediting an atomicity fix; (2) an ACTUALLY-interleaved two-writer test (two futures started before either is awaited) **FAILS on the fake while passing in production** — the second writer clobbers the first. So a "two writers in the same window, both edits land" acceptance criterion is not merely unproven on the fake, it is *unexpressible*; it needs `firestoreForLane()` + `emulatorOnlySkip` — written 2026-07-26 as `test/integration/firebase/repositories/shopping_collaborative_mutation_integration_test.dart`; extend that rather than building a second one. **Caveat: no CI job and no script passes `--dart-define=USE_EMULATOR=true` over `test/integration`** (`run_e2e_tests.sh` targets `test/e2e` only), so every emulator-lane test in the repo is currently skipped everywhere. Treat a lane test as documentation-plus-ready-to-run, never as coverage. What a fake-backed transaction test DOES prove: the handler's base object comes from a server read rather than a client cache — real and worth keeping, just never label it a race test.
- `serverTimestamp()` inside `batch.set(..., SetOptions(merge:true))` does not reliably break the fake — only certain write shapes trip it; let a success test prove it lands.
- Fake CANNOT fire `permission-denied` — acceptable to skip only when the branch is a single `if (e.code=='permission-denied') return null;` above a rethrow with no side effects.
- A seeded fixture must include every field an `orderBy` reads — the fake (like real Firestore) silently drops docs missing it, which can masquerade as a query bug.

### Conscious-skip taxonomy (each discriminant is distinct)
- Static-method orchestrator: skip only when ALL hold — ≤3 calls, no injection seam, each in its own try/catch, no branching beyond the catches.
- Static disclosure whose sync contract is compiler-enforced (renamed `AnalyticsEvents.*`/l10n constant fails analyze/gen-l10n before any test runs).
- Pure-nav affordance (`pushNamed(<const route>)`) — route constant is compile-checked.
- Nth surface adopting an already-proven predicate: prove via `git diff --staged --name-only` — no new surface if the pure-logic file is absent from the diff.
- Mechanical `AppColors→theme` swap: skip only if finder-level assertions are unaffected.
- `SemanticsService.announce` in a fire-and-forget handler is skippable UNTIL the view gains a DI seam or full-shell harness — a conscious skip is dated, not permanent.
- A "sole guard"/"bypass not possible" comment is a claim until a test actually enters that exact branch.
- A comment-only diff owes no new test IF the claim is already pinned by a spy/Fake that would fail-loud if false — verify, don't trust.

### Vacuity patterns — the recurring ways a "passing" test proves nothing
The single most repeated finding across two months of review. Check every new test against this list.
- **Circular determinism.** Calling the same pure function twice, or deriving the expected value from the SAME const the test guards, proves referential transparency, not the invariant. Pin the literal OUTPUT VALUE (`expect(buildId('r1','m1'), 'r1_m1')`, not `expect(buildId(...), buildId(...))`). Same trap for a cost/safety cap: if the expected length is computed FROM the const under test, add one literal pin (`expect(maxCompoundParts, 8)`).
- **Fake-default-same-as-expected.** If a Fake's optional-param default equals the "forwarded" value the test asserts, omitting the arg still passes. Use a sentinel default no real caller would pass (`maxDocuments = -1`).
- **Negative-scope claims need a negative assertion.** "Never includes email/phone" must assert ABSENCE (`toMap().keys` excludes it), not just presence of allowed fields.
- **Boundary tests must straddle the EXACT flip point.** For truncating `.inDays > N`, the flip is between `inDays==N` and `N+1` — a test at `N-1`/`N+2` misses tightening regressions entirely. Assert both `Duration(days:N,hours:12)` (not-yet) and `Duration(days:N+1)` (now).
- **"X does NOT happen" needs proof the code reached the point X could have.** Two different failure paths can share one negative observable (e.g. "strategy threw" vs "strategy not found" both yield empty events) — assert a signature UNIQUE to the intended path.
- **`findsNothing` needs a co-asserted positive render** in the same test, else a build crash upstream explains the absence too.
- **"Returns null on permission denial" needs a positive control in the SAME fixture** — the null could come from an unrelated failure further down the same path.
- **Last-wins/correction tests must assert the LOSER is absent**, not just the winner present.
- **Precedence/weighting tests need inputs where the WRONG alternative gives a DIFFERENT number**, ideally opposite-direction (A: sig1=5,sig2=2; B: sig1=2,sig2=5 → assert weight(A)>weight(B)). Same-value inputs can't distinguish precedence from averaging.
- **A drift guard walking only `vocab → mapping exists` catches forward drift, not reverse** (a mapping the producer no longer emits still compiles). Fix: a POSITIVE test driving the real producer, asserting emitted set == vocabulary.
- **A partition/uniqueness test derived from the SAME curated list the impl was written from cannot fail.** For any `contains()`-based classifier, run a throwaway probe over every sibling name in the real vocabulary — surfaces substring-collision bugs in minutes. In an ORDERED first-match-wins rule chain, also probe for entries SHADOWED by an earlier rule: they are dead code that reads as coverage. **A shadow fix is per-ENTRY, not per-file — re-run the probe over the WHOLE chain after it.** The probe maps every rule literal → its own rule's category and prints mismatches; minutes to write, and the ONLY thing that catches this (BUT-1666 still leaves `tomatpuré` shadowed by veg `tomat` plus a dead duplicate line, twice). A golden-corpus diff adding only the exact inputs the fix targeted is this same vacuity — add one ADJACENT compound per rule touched, including rules the ticket never named (`jordnötssmör`→dairy via `contains('smör')`). **Then audit the corpus against the LITERAL strings the ACs name, one grep each:** BUT-1666 went green twice with 8 of 13 absent, two of those still wrong (closed 2026-07-26: corpus 17→37 cases). A regex guarded by ONE corpus case is minimal-but-non-vacuous; mutate it and count the reds. **When a probe shows the code disagrees with an AC, a passing-id-snapshot corpus gives a third option beyond "encode the code's answer" or "stop":** add the case with the CORRECT expectation and leave its id OUT of `_expectedPassing`. Set-equality still passes, the miss is reported in the nightly artifact's `failures[]`, and nobody can later read it as intended behaviour. Say so in the case notes and beside the omitted id.
- **A "does less work now" claim needs a discriminator test, not a convergence test** — seed something ONLY the naive path would wrongly pull in, assert it's absent.
- **Round-trips must drive the REAL serializer** (`toFirestore()`/`fromMap`), never `copyWith`. A model with two legs (`toJson`/`fromJson` cache AND `toFirestore`/`fromMap`) needs a non-null value asserted through BOTH independently.
- **A test title claiming something the fixture can't distinguish** ("SCALED line", "dest wins", "reverse drift caught by the compiler") — trace whether the fixture is at the default/identity config or the branch is unreachable. Audit names against bodies.
- **A test named as a round-trip that never calls the read-side function** is misleading and a coverage hole — grep test names against what bodies actually call.
- **A two-sided guard needs a discriminator PER SIDE, and a TIGHTENING needs a recall control.** Replacing ASCII `\b` with `(?<![a-zåäö0-9])tok(?![a-zåäö0-9])` fixes two independent halves; a natural corpus exercises only the TRAILING one, so deleting the lookbehind leaves the suite green. Prove each half by mutating one out. Never conflate the two properties a fixture can carry — mutation value ("flips when I delete the lookbehind") vs regression value ("the OLD regex got this wrong"); run the old pattern over every fixture before writing the rationale, because `\b` DOES exist between `å` and an ASCII letter (so `\bsocker\b` matched inside `råsocker`) while an all-ASCII case like `havssalt` was never a regression at all. Every tightening also COSTS recall, so pair each negative fixture with a positive control that pins the tradeoff. **A fixture has THREE possible histories, not two** — matched by the old ASCII `\b` and by the fix (`råsocker`: the two-sided version in between was a recall REGRESSION), matched by neither until now (`havssalt`, `vetemjöl`: pure new recall), or never matched by any (the negatives). Print each candidate pattern and run all three over every fixture before writing a word of rationale. **And first ask which DIRECTION the predicate's cost is asymmetric in:** where a false positive only keeps a line and a false negative deletes it (`looksLikeIngredient` — no fallback branch downstream, allergen-bearing lines), a one-sided boundary is correct and "tighter" is the bug; encode that reasoning in the group comment or the next session re-tightens it. Measured BUT-1661 word list + per-fixture verdicts: archive, 2026-07-25 / 2026-07-26.
- **Firestore numeric aggregates landing on a whole number are stored as `int`, not `double`** — a parser using `as double?` throws and silently drops the row; add one whole-number case (`'average':5` → `5.0`).

### Fake/Mock idioms + the ServiceLocator/GetIt bridge
- `class X implements Y` with concrete bodies is a legitimate Fake. The mocktail ban is specifically a concrete `@override` on `extends Mock` (blocks `when()`) — narrow exception: a pure call-count "counting fake" never `when()`-stubbed on that method, or a non-nullable getter a bare Mock would noSuchMethod-crash on.
- `extends <ConcreteClass>` with an `@override` body is a legitimate SUBCLASS SPY, not the banned pattern (the ban is about mocktail `Mock`).
- Lazy `tryGet` fields cache on construction — register fakes BEFORE constructing the SUT.
- Callback-based async APIs: capture the named callback via `invocation.namedArguments[#name]`, invoke synchronously inside `thenAnswer`.
- **The GetIt→DIContainer bridge gotcha (recurring — analytics/tag-overrides/correction-snapshot/import chokepoints):** many singletons (`AnalyticsService.tryLog`, `ImportManager`'s rate limiter/cache/normalizer, `TagEditingService`'s override log) resolve via the PRODUCTION `ServiceLocator` (`application_provider.dart`, a `DIContainer` over `GetIt.instance`) — NOT the plain `TestServiceLocator.initialize()` path. A mock registered only via `TestServiceLocator.registerMock/registerSingleton` is INVISIBLE there; captured events stay empty, test silently proves nothing. Fix: `prod.ServiceLocator.initialize(DIContainer())`, then register into `GetIt.instance` AFTER; tearDown = unregister + `ServiceLocator.reset()`. Check what else on that path touches the locator before bridging into an existing file — an unstubbed dependent read outside try/catch can throw.
- Fire-and-forget writes to `FakeFirebaseFirestore` need microtask draining — two `await Future.delayed(Duration.zero)` (or `pumpEventQueue()`); not the banned real-time wait.
- **A new fire-and-forget telemetry call at a chokepoint reliably ships with ZERO tests.** Add a capture-test: fires-once-with-params on the happy path, fires-nothing on the negative path. "Just telemetry, no seam" is usually false — trace the resolution chain.
- **A funnel-ATTRIBUTION fix (`source:` tags, "this path was invisible") is only as good as its path enumeration, and it has TWO failure directions.** Grep every producer of the event before believing the ticket is closed (BUT-1670 tagged one menu→list path and left a second emitting nothing). And an idempotent regenerate/replace path that logs `itemCount` "added" events re-counts every unchanged line — assert the second run logs only the DELTA. **Confirmed SHIPPED unfixed on BUT-1670** (`MenuShoppingListGenerator._logGenerationAnalytics`): `isNewList` correctly suppresses the CREATED event but the item loop still fires `items.length` events on every regenerate, while `updateList` replaces items wholesale — so the funnel the ticket exists to fix is inflated by the fix. The delta is already computable there (the `previous` bought-status map holds the prior keys), so "no seam" is no excuse. The suppression half ("only a genuine false→true transition logs") is the cheapest VM test and the one most often skipped. **Grepping the event method name across `test/` and getting zero hits IS the finding** — run it before crediting any analytics ticket.
- **A safety-critical method covered ONLY via `mockService.method` `verify()` in a caller's test proves WIRING, never the wrapped CONTRACT.** Grep for the new method NAME at its own service/repo layer. The same hole opens one layer up whenever a change introduces a new RESULT TYPE (`ProfileLookup`, a status enum, a completeness flag): the consumer's suite hand-constructs `Status.x(...)` fixtures, so the PRODUCER — often the single line that ever emits the interesting value — ships with zero tests and stays deletable green. Grep for the TRUE-direction assertion (`expect(flag, isTrue)`, `status, Status.x`), never just the type name; on BUT-1663 all three new repo tests asserted `settingsUnavailable, isFalse` and the `copyWith(settingsUnavailable: true)` line that the whole feature rests on had none. A parse/cast failure seeded into `FakeFirebaseFirestore` (a String where a Map is read) is usually enough to reach such a catch block.
- `collectionGroup` on the fake is safe for index-free `.limit(N).get()` without `where()`, AND (^4.1.0+1) for plain `collectionGroup`+equality — narrower than "always needs emulator."

### Disposal & lifecycle guard idioms (BaseViewModel family)
- `BaseViewModel` already guards disposal TWICE (`clearError()` and `notifyListeners()`), so a subclass's OWN third guard is usually untestable-to-fail — `dispose()→clearError()→returnsNormally+notified==0` can't go red from removing it. Only test a disposal guard protecting an OBSERVABLE effect no base guard blocks (e.g. a late stream emission mutating a private field BEFORE the guarded notify — assert the STATE stays unchanged).
- Two quadrants when sweeping a guard across many VMs: (A) delegate disposed BY this VM's own `dispose()` — test `returnsNormally`+`notified==0`. (B) delegate is a SHARED SERVICE outliving the VM — `returnsNormally` is VACUOUS; assert the service's error SURVIVES the VM's disposal instead.
- A class with BOTH a local `_isDisposed` (set at the START of its own dispose) and inherited `BaseViewModel.isDisposed` (flips only inside `super.dispose()`, often LAST) must have any new guard use the SAME flag its own callbacks use. Migrating `ChangeNotifier`→`BaseViewModel` turns the old `throwsFlutterError` post-dispose-notify test into `returnsNormally` — also assert the listener was NOT invoked, or it can't tell "no-op" from "leaked".
- A VM shadowing `error`/`hasError` must be proven by driving a FAILED base `executeAsync` (populates `super._error`) — seeding only a service-level error while base stays clean can't catch a dropped override. First check the VM calls base `executeAsync` at all; if error routing is fully manual, `super._error` is dead and this pattern doesn't apply.
- `executeAsync` RETHROWS on failure (not null). Prove it indirectly via a caller that only retries on THROW (assert attempt count) — a bare try/catch around the call is vacuous re: rethrow-vs-null.
- **A `dispose()` that clears DATA (not just controllers/timers) creates a use-after-dispose window for any long-running op still holding the object** — read the collaborator's dispose body before trusting "just a leak fix" (`FormFieldsManager.dispose()` also does `_values.clear()`). Test: dispose mid-operation (after the op's last await point), assert the WRITE still carries the user's data. Check whether the op's own `if (_disposed)` guards are even live — a manager the owner never disposes has permanently-false guards.
- **A "disposes its children" test asserting only `returnsNormally` on a still-callable method is vacuous.** Materialize the child (e.g. `state.manager.controllers`) BEFORE dispose, then assert it is dead: `expect(() => controllers.first.addListener(() {}), throwsFlutterError)` — `ChangeNotifier.addListener` debug-asserts not-disposed, so the assertion flips when the dispose line is reverted.
- **A new throw-on-disposed guard inside a shared builder is only safe at callers that catch.** It converts silent corruption into an uncaught exception everywhere else — enumerate call sites yourself; a comment claiming "every caller sits inside a safeExecute" is a claim, not a fact (BUT-1667: `RecipeFormState.createRecipe`'s unguarded `RecipeFormCoordinator.syncToCollaborative` caller was only guarded on the third pass, and never got a test — `RecipeFormCoordinator` has no test file at all). Pair the guard test with a probe of each call site's error handling. Two things that make such a caller look safe when it isn't: (a) its OWN `_disposed` flag can be dead — grep that someone actually calls `dispose()` on it, and re-grep after the fix lands rather than trusting the earlier finding (`RecipeFormCoordinator.dispose()` had zero `lib/` callers until `RecipeFormViewModel.dispose()` gained the call on 2026-07-26; its guard now has both terms live); (b) `ChangeNotifier.notifyListeners()` after dispose is a DEBUG-ONLY assert (release sets `_listeners` empty and no-ops), so a post-dispose chain that "throws in tests" runs straight through in release to the next statement. Never conclude "unreachable — it would have thrown earlier" from a debug-mode trace.
- **A disposal guard added to one method is unfinished until its TWIN on the same class is audited** — grep the class for every `_state.set*`/`notifyListeners` outside a `!_disposed` check before crediting the fix. Worked case (BUT-1667, closed 2026-07-26): `saveRecipe` got `if (!_disposed) _state.setSaving(false)` while the sibling `forkRecipe` read `_disposed` nowhere, so a fork in flight at form close hit the new `createRecipe` StateError → `safeExecute` → null → `setError()`/`finally setForking(false)`, both UNGUARDED on a disposed `ChangeNotifier` — the guard turned a silent bad write into an uncaught throw on the untouched path. The test is a VM-level fork gated on `addUnifiedRecipe`, disposed mid-flight, completed with a FAILURE (the failure arm exercises both `setError` and `setForking`; the success arm only reaches `setForking`), asserted with `await expectLater(forking, completion(isNull))` + `expect(vm.error, isNull)`.
- **A `manager.dispose()` fix has TWO halves and the wiring half is the one that ships untested.** A manager-level test calling `manager.dispose()` by hand proves the guard, never that the owner ever calls it. Probe by deleting the owner's `_xManager.dispose()` line: if every suite stays green (BUT-1667's `RecipeFormViewModel.dispose()` → 304 tests still passed), the entire fix is deletable. Two traps when writing the owner-level test (both hit on BUT-1667, closed 2026-07-26): (1) **"no write reaches the service" is NOT the discriminator** — with the owner's `dispose()` line deleted the save still writes nothing, because the disposed `RecipeFormState.createRecipe` throws first. The observable that flips is that the returned future **throws instead of resolving null**: the un-disposed manager's `if (!_disposed) _state.setError(...)` then notifies a disposed `ChangeNotifier` → `A RecipeFormState was used after being disposed` escapes at form close. Assert `expect(await saving, isNull)` and keep the `verifyNever` writes as the intent, not the trigger. (2) **you need an await seam the owner's constructor actually exposes.** `RecipeFormViewModel` injects only `recipeService`, and the no-image save path runs synchronously all the way to the write — so gate `StorageService.uploadRecipeImage` (registered via `TestServiceLocator`) and force the upload branch with `vm.imageManager.addPendingImage(File('x.jpg'))`. Pair it with a `verify(uploadRecipeImage).called(1)` control or the test also passes when the save bails at the TOP guard.
- **A queue/`Completer` whose `.future` is never awaited is dead plumbing** — grep for `.future` before believing a "waits for the in-flight op" comment. A polling loop returning a cached `_lastResult` silently drops the second caller's work AND can hand back a previous operation's result; `completeError` on an unlistened completer also raises an uncaught async error to the zone. **Fixing the double-complete without a test is the common shape** (BUT-1669): re-inserting the removed `completer.complete(result)` AND deleting the `if (!completer.isCompleted)` guard both stayed GREEN across the manager + VM suites, because no test ever enters the `_isSaveInProgress == true` branch. Any concurrency fix needs the second caller actually launched — assert BOTH futures resolve and that the second one's value came from the save it waited on, not a prior cycle. Watch the dispose exit: `if (_disposed) return false` drops the waiter out of the poll loop early, so it returns the PREVIOUS save's cached result and the UI reports success for a save that never ran.
  **Test recipe (BUT-1669, all three mutants verified red 2026-07-26):** run a WARM-UP cycle first so a stale-cache regression has a wrong value to hand back, then gate the write on a `Completer`, launch caller B, and settle. Three assertions, three distinct mutants: `same(inFlight, queued)` + no error catches the re-inserted double-complete (`Bad state: Future already completed`); `queued == null` after `dispose()` catches BOTH deleting `_completePendingSaveOperations(null)` from `dispose()` (test HANGS to the 60 s timeout — that timeout IS the red) and reinstating a `_lastSaveResult` (`Expected null, Actual Recipe`). Close with a `captureAny()` on the write asserting the overlapping pair produced exactly ONE persisted id, equal to the id both callers return — the double-tap-makes-two-recipes invariant a call-count `.called(n)` only gestures at.

### Contract pinning: selectors, ordering, equality, revert
- Every `field == expected` selector needs THREE pins: matched-key reused, unmarked-collision untouched, marked-for-different-key untouched+new-created.
- `==`/`hashCode` tests need an equal pair (equal + same hashCode) AND a deliberately-unequal instance — equal-pair-only passes even if `==` regressed to `=>true`. Watch `hashCode` hashing a collection field by IDENTITY while `==` compares by CONTENT — share instances so the tested field is the only variable.
- Ordering contracts need `verifyInOrder`, not call-count.
- A revert-to-start test must mutate first, THEN revert, then assert.
- Method removed+replaced: audit the deleted group with a test-by-test successor map — auth/permission branches are easiest to silently drop.
- `expect(() => asyncFn(), throwsA(...))` without `await` can pass spuriously — use `await expectLater(...)`.

### Import & correction-capture pipeline
- SSRF host-filtering and decompression-bomb caps are running invariants across every import surface.
- A CTA/UI test proves the LABEL, not the ACTION — assert wire-level dispatch separately (extract a `@visibleForTesting` pure helper) when a shared widget/VM hardcodes an attribution tag for "the common case."
- **Correction-snapshot/parse-cache keys sharing a placeholder across unrelated imports silently collide** (e.g. text+photo both keyed on the same constant placeholder `sourceUrl`) — second write overwrites the first's training snapshot with no error. Test two same-kind imports in sequence, assert retrieval returns the FIRST's data.
- **A wizard rebuilding an editable buffer from a prior step unconditionally on forward-nav loses edits on back-then-forward.** Forward-only suites are structurally blind — add one back→edit→forward preservation test; guard with a "did selection actually change" check.
- **An ASCII-`\b` fix is a per-REGEX fix, not a per-file one.** After any Swedish word-boundary repair, grep `\b` across the same file and the sibling detectors in the folder — the import layer carries 3 independent `looksLikeIngredient`/measurement-matcher copies. Single-letter unit tokens (`l`, `g`, `st`) under `\b` misfire on any å/ä/ö neighbour, which silently kills legitimate component headings. **Reproduced against live production code 2026-07-25, still unfixed after BUT-1661 repaired only `RecipeSectionDetector`:** `IngredientLineDetector.looksLikeIngredient` (`lib/services/import/heuristics/`, live on the assisted-import and url-import paths) returns true for `Lök:`, `Rödkål:`, `Kål`, `Gäddan` and even the instruction header `Gör så här`. Its own suite passes because every fixture is ASCII-bounded — run the å/ä/ö heading probe, not the suite.
- **A boundary repair inside a shared predicate changes behaviour at EVERY call site, so enumerate them before scoping the tests to the ticket's own sentence.** `RecipeSectionDetector.looksLikeIngredient` has six: two decide the OPPOSITE of "is an ingredient" (`text_import_strategy.dart:686` `if (looksLikeIngredient(label)) return null` kills a section label; `multi_recipe_splitter.dart:120` returns false), one breaks a title loop (`:376`), and `multi_recipe_splitter._looksLikeCompleteRecipe:173` COUNTS matches against `_minIngredientLines` — so a recall-widening fix moves where multi-recipe splits happen. Only the detector's own suite was extended on BUT-1661. Also grep for COMPENSATING WORKAROUNDS whose comments now assert the fixed bug as live: `multi_recipe_splitter.dart:176-178` still reads "needed because looksLikeIngredient misses unit-less, åäö-leading lines like '2 ägg'". A stale comment of that shape is how a future session re-adds the workaround.
- **Rate-limit metering: enumerate ALL call sites of the limited operation** — assisted-import, cache-hit, social-platform paths have each silently bypassed or double-charged the same bucket.
- **A circuit-breaker over a parallel `Future.wait` batch must not discard already-materialized results** from the same batch when it trips mid-batch — a success after the trip point can be dropped though its side effects already happened.
- **A "retry" wrapper keyed on THROWN exceptions is dead over an API signaling failure by return value** — check what the wrapped op does on failure first. Wrapping an ALREADY-STARTED `Future` in a retry extension can never re-run it.
- **A cross-copy "single source of truth" test must actually READ every copy it claims to unify** — an unexported duplicate elsewhere can still drift silently.
- Windows `flutter test`: `/c/tools/flutter/bin/flutter test <forward-slash-path>` via the Bash tool works directly, no wrapper needed.

### GDPR / export section contract
- Every export section needs THREE proofs: (1) seeded → count present AND the genuine PII field round-trips verbatim; (2) ownership-negative → a doc owned by ANOTHER uid is absent; (3) empty-safe → `total==0` AND `containsKey('error') isFalse` (every manager wraps its body in try/catch→`{'error':e}`, so this catches a silent degrade a bare "section exists" test would miss).
- Redaction paths (e.g. FCM token → 10-char prefix + `[redacted]`) are the SECURITY invariant and outrank another happy-path test — check these first when reviewing a partial export manager.
- Where counterparty data is a DECIDED inclusion (not redaction), write the test that PROVES inclusion, with a comment citing the decision.
- A two-query union+de-dup section needs FOUR fixtures: sent-only, received-only, self (both legs match the SAME doc — the only row catching a de-dup regression), foreign (ownership-negative).
- Derive caps (`getLimitForType('<type>')`) for both fixture size and assertion — never hardcode; re-tuning a cap is config, not a regression. Two-leg fixtures derive per-leg from the cap and ASSERT the premise (`perLeg*2 > cap`, `perLeg <= cap`).
- **Truncation flags need all THREE boundary points AND a positive control per source leg.** `truncated` is an N+1 probe (`fetch(cap+1)`, `rows.length > cap`): pin below-cap, exactly-at-cap (complete → flag ABSENT) and cap+1 (flag present, payload trimmed). A "does NOT stamp truncated" test alone is vacuous — deleting the flag keeps it green; the dangerous direction is a clipped bundle claiming completeness. An N-leg OR needs N positive tests: the skipped leg is the unproven one, and covering only the LAST catches collapse-to-first but never collapse-to-last. Two more that the boundary triple misses: (a) `total_count` must be asserted EQUAL to the shipped payload's length (a `CappedExport.length` regression counting the pre-trim fetch ships `cap` records under a `cap+1` manifest); (b) for a multi-leg section where each leg carries the cap independently, the single highest-value case is **neither leg over cap but COMBINED over cap → flag ABSENT** — that is exactly what the retired merged-length comparison got wrong, and no per-leg test can reach it. (Worked example: `preferences_export_manager_test.dart`, BUT-1662 — `exportRecipes`/`exportMenus` legs plus the four notification sections.)
- **When a sweep extracts a shared capped-read primitive, test the primitive directly** (probe size, trim, both boundary sides, unknown-type fallback, error propagation); per-section tests then prove only WIRING, so spend the rest on sections with new logic (a multi-leg OR) and on any leg whose fetch param is NOT the usual name (`maxLists`, `limit:`) — a rename-shaped slip drops the cap silently, so pair it with a sentinel-default fake. Four audits the diff hides (all live on BUT-1662 at commit time; detail in archive): (1) grep the WHOLE swept file for the old pattern — un-swept siblings emit NO `truncated` key, i.e. silent clipping, worse than the bug being fixed; (2) **a sweep spanning several files lands its tests in only ONE of them** — grep the method name across `test/` per swept FILE, not per ticket, zero hits IS the finding (BUT-1662's four rewired `preferences_export_manager` sections sat at zero hits for two review rounds; a grep proof beats a mutation run there, because reverting `if (entries.truncated)` to `if (entries.length >= limit)` provably cannot go red when nothing calls the method). **Filling that hole is cheap and table-driven:** one `_CappedSection` record per section (cap type, payload key, seed closure, invoke closure) looped into a `group`, times the three boundary tests. Keep the shared `extends Fake` seeding each section's rows in a SEPARATE nullable field that throws `UnimplementedError` when unseeded — then a test wired to the wrong sibling method fails loudly instead of passing on another section's rows, which is what makes a table safe to loop; (3) check whether `cap + 1` FANS OUT into a subquery per extra doc; (4) re-read the primitive's own doc comment, which (3) usually falsifies.

### Settings-hydration & sentinel-parameter template (recurring: BUT-1220, 674, 1322, 1610)
Any field persisted via a private settings sub-doc needs: (1) a hydration test seeding the sub-doc DIRECTLY; (2) a corrupt-value test that ALSO asserts a SIBLING merged field survives (the merge is one `copyWith` in one try/catch — a naive parse of the corrupt field can abort the WHOLE merge, invisible if you only check the corrupt field's own null-safety); (3) a save-path test asserting the settings doc has it AND the public doc does NOT (privacy-leak guard) + round trip; (4) if the field has 3 serialization surfaces (Firestore/JSON-cache/copyWith), each needs its OWN test.
Sentinel-parameter contracts (`Object? field = _unset`) need both quadrants at the layer where omission is possible: omit→preserved, explicit-null→cleared. Prefer capturing the forwarded ARGUMENT IDENTITY against the sentinel (`identical(captured, Sentinel)`) over a downstream no-op — a regressed VM forwarding an in-memory null instead of the sentinel can coincidentally suppress the same effect.

### Age/maturity/consent gates
- A field moved client→CF-authoritative: invert the old round-trip into an ABSENCE assertion on EVERY client-write surface (`toFirestoreEditable`, `toPrivateSettings`, any merge map) — verify non-vacuous by confirming the field still appears in base `toFirestore()` (so it COULD leak).
- "Infra error" vs "explicit rejection" needs a TYPED discriminator flag asserted on BOTH branches — a bare boolean can't tell them apart.
- "Must NOT re-fire on resume/already-verified" needs BOTH `verifyNever(gate call)` AND the positive downstream effect in the SAME test — asserting only the return value is green-blind when the stub defaults to success anyway.
- A "quiet/never-throws" method's contract is proven by asserting the user-facing error field stays null on EVERY failure branch.

### Menu & tagging domain
- Weighted-random selectors: assert WEIGHT MATH via a `@visibleForTesting debug*` hook, never the sampled outcome (an assertion on which item got picked from a `Random` draw is an automatic vacuity flag). Pair with: unrated equals the 1★ value (never-penalized, not just selectable); ceilings pinned via `closeTo` at extreme inputs so a no-op multiplier fails.
- **Any feature persisting entity ids later intersected with a live collection (present-diner ids, dislike lists) needs a ZERO-INTERSECTION test** — stale ids usually fail OPEN (empty filter = no filtering), the dangerous direction for allergen safety.
- **A "conservative fallback" to a shared `defaults` const is only conservative if that const is a SUPERSET of what the happy path would have produced — open the const and check.** `UserAllergenPreferences.defaults` tracks just {gluten, mjölk, nötter, jordnötter} with `includeUnknownInMenu: true`, so aborting a household union into it DROPS the resolved members' real allergens and re-enables UNKNOWN recipes. Test the abort path against the *readable* members' allergens, not only the unreadable one's.
- **A widen-not-replace fallback needs its PASSTHROUGH half asserted, not only its added half.** Tests that pin "the safety floor got added" stay green if the preserved field is quietly swapped for an empty default (BUT-1663 degraded path keeps `dietary: unionDietary` — no test covers it, so `const {}` would silently serve meat to a vegetarian member). Assert every field the degraded object claims to carry forward. Same sweep for a complete-vs-degraded discriminator flag: check EVERY early-return in the method, not just the ones the ticket touched — a `memberIds.length <= 1` short-circuit still reporting `complete` from absent data reinstates the bug in a corner.
- **Anchor/cursor guards (`if (index < anchorIndex) continue;`) need a test AT the anchor, and the fixture must make the two code paths land on DIFFERENT days.** With a single recipe the chronological fill also targets the anchor day, so an off-by-one (`<=`) is invisible — use two recipes plus a `requiredTags` pin so the pinned one is provably not just "the first one".
- Feature-flag OFF paths are a systemic blind spot: `tryGet<FeatureFlagService>() ?? true` means the OFF branch is untested unless a fake flag service is explicitly registered false.
- A config-version-gated rebuild guard needs both directions: newer→rebuild, same→no-rebuild. If a version is captured once but RE-DERIVED later instead of threaded through, a concurrent run can stamp the wrong version.
- An "X lands first" ordering comment is unproven without a two-candidate COMPETING test.
- Denormalized-projection tests: capture via `captureAny()`+`.captured.last`; cover the NULL-CLAMP arm (removing the last vote → null, not 0); prove EQUAL-WEIGHTING with ASYMMETRIC inputs (symmetric inputs can't distinguish equal-weight from count-weighted).
- A repo→VM re-key seam (poolKey→recipeId) is the highest-value untested point when the repo test asserts one key-shape and the widget test injects the other directly.
- Adding a versioning field to old fixtures is usually INTENT-PRESERVING under a new staleness guard, not weakening — audit ALL fixtures of that type when such a guard lands.

### Firestore cost, index & cascade patterns
- A declared composite index needs its own assertion (the index array, in a test) — fakes can't catch a missing composite. Also assert `queryScope` (COLLECTION vs COLLECTION_GROUP) alongside field order.
- A merged/idempotent cascade batch that unconditionally `update()`s a doc it assumes exists can throw NOT_FOUND and fail the WHOLE batch if that doc is already gone — test the gating doc exists but the TARGET doesn't.
- A denormalization write via dotted-path transactional `update` needs a test asserting an UNRELATED sibling field SURVIVES — proves scoped merge, not whole-doc rewrite.
- A CF trusting a doc field for a security decision is only as strong as the Firestore RULE validating that field on create — confirm the rule pins it before crediting a "backstop for tampered clients."

### CF/TS-specific
- A new emulator-integration test must be wired into the CI chain on THREE fronts: the granular `test:integration:*` script, the composite chain CI actually runs (e.g. append to `test:rules:all`), and the workflow's `paths:` trigger list — unit-test runners auto-discover `test:*` but EXCLUDE `test:integration:`/`test:rules` prefixes.
- In integration tests, order the existence assert BEFORE the first dereference of a possibly-missing doc — a `data()!` throws a raw TypeError one line before the friendly assert runs.

### Multi-select / bulk-action wiring
- VM tests + card tests can pass while the GLUE (snapshot/order/callback) is untested at widget level.
- Selection-guard tests need the owner's OWN tile, not all-strangers. Clear-on-cancel: assert count returns to the ORIGINAL, not zero.
- Copy-paste id-field mismatches are invisible unless a fixture makes the two fields DIFFER.
- Async error stubs: `thenAnswer((_) => Future<int>.error(...))` — never `thenThrow` (sync) nor `async => throw` (type-erased).

### Extraction seams & duplicated-logic-across-surfaces
- Pure decisions locked in a DI-heavy widget → extract `@visibleForTesting static` instead of a DI bridge.
- A "pure structural split" makes private behavior a public in→out contract — that's when tests newly apply.
- **Duplicated-logic trap: when the SAME behavior is independently re-implemented in 2+ classes, grep every `_resolve*`/init copy and demand a test PER COPY.** Copies WILL diverge silently (observed: one gains a range guard the other lacks).
- **LIVE-PATH CHECK — do this BEFORE reviewing/writing any test for a bug fix.** Grep the call chain from the actual view/widget down to the write and confirm the fixed method is ON it; a fix landing on a parallel facade with no `lib/` callers passes its own test and ships nothing (BUT-1665). When tests drive one method but production calls a DIFFERENT one, make the live path DELEGATE to the tested tail. **Then check the rewired layer has its OWN test file** — grep the CLASS NAME across `test/` and treat zero hits as the finding. A well-tested caller and a well-tested callee do not add up to a tested seam.
- **A "reads live state, not the caller's cache" contract is only tested if the fixture makes the two DIFFER.** The whole `ShoppingItemOperationsModule` file (five collaborative mutators, the live UI write path) had zero tests until 2026-07-26 and a `live`→cached `list` re-point stayed green across 78 tests in three "covering" suites. The fixture that catches it: cached copy = what `readList` returns, stored doc = cached PLUS a tick on one item PLUS an item the cache never saw. Both deltas matter — the extra item catches add/remove (silently dropped) and the tick catches update (silently reverted); an update aimed AT the cache-invisible item is the sharpest case, since a cached-base `map()` matches nothing and the user's edit vanishes with no error. Stamp fields (`lastActivityByUserId`) need a THIRD actor seeded so neither party's assertion is vacuous.
- **An atomicity fix is tested at the layer that OWNS the atomicity — and on the fake that layer is UNREACHABLE.** Stubbing the service seam and applying the mutator by hand only proves the mutator is a pure function of `live`; it never runs `runTransaction`/retry/not-found. Driving the real module against `FakeFirebaseFirestore` looks like it closes that gap but does not (see the no-op-passthrough principle above) — the atomicity half needs the emulator lane, and the fake-backed tests should say in a comment that they pin the live-base read only. A transaction-runner typedef injected as a constructor seam IS legitimate: it is `null` in production, defaults to the real `firestore.runTransaction`, and is the only way to raise the platform codes (`unavailable`, `deadline-exceeded`, `aborted`) the fake cannot — keeping the real fake's collection ref so the fallback's reads/writes stay honest. But it seams out the runner, not the transaction, so it never exercises the production `runTransaction` call itself; pair it with one emulator-lane test or the production binding ships unproven. Exceptions thrown INSIDE the handler propagate as themselves, so an `on FirebaseException` fallback cannot swallow a `PermissionDeniedException` — good, but assert it.
- **A permission/escalation guard added to ONE method of a pair must be checked on its sibling.** BUT-1665 put `_requireNoPrivilegeEscalation` on `updateCollaborativeList` (entity-taking) but not on `mutateCollaborativeList` (mutator-taking), though both persist a caller-shaped whole document. Arbitrary-callback APIs are the easier bypass, not the harder one. Before rating it Critical, read the matching Firestore rule — a `!diff().affectedKeys().hasAny(['ownerId','memberPermissions'])` clause makes it defence-in-depth asymmetry rather than an exploit.
- **Converting a per-item write into a per-item TRANSACTION makes every existing parallel fan-out over the SAME document pathological.** Grep the callers for `Future.wait` before approving: N concurrent transactions on one doc contend, exhaust `maxAttempts:5`, throw `aborted`, and an all-or-nothing `Future.wait` caller rolls its optimistic UI back even though some writes landed. **Still live and unfixed at `ShoppingItemManagementModule.uncheckAllItems` (`Future.wait` over `repository.updateItem`) as of 2026-07-25** — the pre-transaction last-write-wins version could not fail this way; the fix is ONE `mutateCollaborativeList` with the model's own bulk method. The test that catches it drives the bulk action against a collaborative list and asserts every item landed. Related plugin fact: `runTransaction(timeout:)` bounds only the DART handler (native semaphore in `TransactionStreamHandler`), NOT the server round-trip — shortening it does not make an offline write fail faster, so don't let a test or doc comment claim it does.
- **A shared cache reused by a STRICTER new reader launders the weakest writer's output.** When a new method promotes a cached object into an authoritative status (`found` meaning "absence is now a user DECLARATION"), enumerate every writer into that cache before trusting it. `UserService._profileCache` is also filled by `getUserProfiles`→`FirebaseUserRepository.fetchProfiles`, which never merges the private settings sub-doc — so once the owner's own 30-min entry expires or is evicted, a batch roster read re-caches a settings-less copy of the SIGNED-IN user and their declared allergens silently vanish from the household union. Test shape: seed the cache through the OTHER writer, then assert the new reader's status/flag.
- Consolidating duplicated per-caller logic into ONE shared widget/helper: test the LOGIC on the shared host once (don't replicate per caller), but add a cheap render+side-effect test on each OLD host proving it still embeds the shared one.
- A crash-safety invariant behind heavy widget scaffolding (e.g. Dropdown's "exactly one item with this value") is better pinned via a small extracted `@visibleForTesting` pure helper than a brittle full-pump assertion.

### One-off gotchas, Windows/runner notes, and the revert-probe technique
- `Semantics(label:)` wrapping a tooltip'd button MERGES into one node with a concatenated label — match with `RegExp` (never exact String), bracket `bySemanticsLabel` with `tester.ensureSemantics()`/`handle.dispose()` in the SAME test.
- Optional-override params with an l10n `??` default: assert an injected override renders AND `find.textContaining(<default's unique substring>)` findsNothing — a shared substring makes the default-path test blind to whether the override threads through.
- A `GlobalKey` preventing State recreation is tested behaviorally: drive the state-changing event that WOULD recreate it, assert continuity survives — never assert on the key itself.
- **"Derives from a scaled/filtered list" claims need the list to provably DIFFER from its source** (factor ≠ 1.0) — testing at the default/identity config is structural blindness.
- A copy-SPLIT (two strings sharing a suffix) needs an assertion on the substring UNIQUE to each.
- Real `.xlsx` stores text via shared-strings (`t="s"`), not `inlineStr`.
- Age-boundary tests must pin the exact legal threshold on BOTH sides, not just far-side values.
- `export 'stub' if (dart.library.js_interop)` services: test only the stub's no-op contract; the web state machine is unreachable from VM tests.
- **Revert-probe (the reliable non-vacuity proof):** copy the production file to scratch, string-replace the fix OUT, run the affected suite, confirm EXACTLY the expected test(s) go red at a unique assertion, restore and byte-verify with `cmp`. Construct the REAL object under the exact constructor wiring the bug lived in. Batch probes in one run only when each fails uniquely; separate when they share a code path. Back up IMMEDIATELY before editing — a parallel session may be editing the same file.
- **When you are told not to touch `lib/` (or the plan-threshold gate refuses the edit), do NOT route around it.** Use a FAITHFUL REPLICA probe instead: copy the method body into a throwaway `test/zz_scratch_*_test.dart` (test files aren't gated) with the one line under probe swapped for a `Function` parameter, and open with a CONTROL test asserting the unmutated replica agrees with the real production function on every fixture — without that control the replica proves nothing. **This scales to a WHOLE CLASS** (used for BUT-1669/1667, 2026-07-26): `cp lib/X.dart test/.../zz_scratch_x_replica.dart`, rename only the class + its constructor, then `cp` the real suite beside it and sed the one import + the type name. Every `package:butlery/...` import resolves unchanged from `test/`, so the replica is byte-faithful; run the copied suite once UNMUTATED as the control (55/55 green proved the VM replica faithful), then mutate. It is blocked only when a mixin declares the type (`RecipeBackwardCompatibilityMixin` requires `RecipePersistenceManager get persistenceManager`, so a renamed replica can't be swapped in one layer down). Delete the scratch pair and re-grep the production file for the mutated token afterwards. Then run each mutant and print which fixtures flip. This also probes mutants the ticket didn't ask for (each HALF of a two-sided lookaround) in the same run, which a real file edit makes tedious. Delete the scratch files and `md5sum` the production files against the backups in the same call as the cleanup.
- **Cheapest probe of all when the SUT already injects the collaborator: mutate the INJECTION, not `lib/`.** If the bug is "the mutator built on X instead of Y", a throwaway harness that feeds the mutator X through the existing constructor seam reproduces the buggy output exactly, with the REAL production method bodies running. No lib/ edit, no replica, no control test needed (the bodies are genuine). Used 2026-07-26 to drive all six `ShoppingItemOperationsModule` collaborative tests red in one run. Applies whenever the differing value arrives as a constructor callback's argument.
- **Write throwaway probes with the Write tool, never a bash heredoc, and use RAW Dart strings (`r'\bfoo\b'`).** Backslashes silently die crossing the Bash layer even inside a quoted `<<'EOF'`: `RegExp('\\b$w\\b')` arrived as pattern `socker` with both boundaries GONE, so a probe reported "the old regex never matched" for every fixture and would have had me file a false finding against correct test comments. Always `print(re.pattern)` in a regex probe and eyeball it before trusting a single result.
- A `TimeoutException ... during "loading"` with 0 tests run is compile-bound (~12min shared `lib/` compile), not a hung test — split the invocation per-file to confirm.

### Firestore-rules `.ts` suites (emulator-gated)
- Every `&&` clause in an `allow` rule gets a failing test; every `cannotModify`/`hasRequiredFields` list needs a test PER FIELD.
- A failure-only update suite can be silently over-restrictive — pair denials with an `assertSucceeds` on a mutable field.
- The emulator persists docs ACROSS invocations — suffix create-test ids with a per-run `RUN = Date.now().toString(36)`, or a fixed-id create silently becomes an update on the 2nd run.
- These are hand-rolled `npx ts-node` runners against `127.0.0.1:8080` — time out without `firebase emulators:start --only firestore` running first.
