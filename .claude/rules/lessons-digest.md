- An audit agent's claim about a tool's OUTPUT FORMAT is a guess until reproduced — run the real tool and test the regex against a real line before "fixing" a parser.
- Feedback right after a deliverable may target the TOOL/process, not the one artifact — disambiguate "fix this output" vs "improve the capability" before acting.
- A multi-part agreed initiative gets ONE written plan before any slice ships — chat scrollback is not a backlog.
- Every proposed improvement must name its mechanical trigger; upgrading an optional command is convenience, not infrastructure.
- Never prune a young system for inactivity — the observation window must exceed its natural cycle (tune now; keep/cut only after 2–3 cycles).
- Don't hand the user judgment/labor you can derive yourself; defer only product intent, irreversible actions, or external facts.
- Bash `cd` persists across calls — use absolute paths.
- A 403 naming a permission can be a WRONG-IDENTIFIER bug, not a credentials bug — a project's display NAME and its real id can differ. Resolve the identifier against `.firebaserc`/`projects:list` BEFORE touching credentials, and before sending the user to fix their account.
- A hook on a RELATIVE path stops firing once Bash cwd drifts into a subdirectory, and a PreToolUse failure is NON-BLOCKING — the firewall then passes destructive commands silently. Wrap every hook command with `cd "$(git rev-parse --show-toplevel)"`.
- Verify Edits actually landed (`git diff`) before committing — never trust the commit-message claim.
- A multi-edit script that asserts before its single write loses EVERY edit when one search string is wrong — even the matched ones, and comment-only edits fail SILENTLY (no test, no analyzer). Grep the changed TOKEN and paste the count after any edit with no test.
- "Unreferenced" must be proven against the WHOLE repo, never a hand-picked subset.
- Run arch gates locally before committing UI widgets.
- When the user asks for a new mode, deliver ONE mode — no "normal + extra", no spare variants.
- "Map the workflows" means full coverage against a stated universe — never silently curate a sample.
- When citing a deterministic tool's verdict (router tier, gate, test), RUN it and paste output — never assert what it would say.
- A subagent naming a file as "the X path" proves existence, not routing — read the client orchestrator's tier/fallback structure yourself before asserting what runs first (cost/privacy claims always get direct verification).
- `curl` is a DIFFERENT CLIENT from the app — its 403/empty page is not your feature failing. Reproduce through the client the feature actually uses (headless browser, real UA, JS on) before calling a site blocked. A page-classifying probe needs TWO independent markers or it measures the crawler (BUT — 2026-08-01).
- A blocked gate is a STOP, not a puzzle to route around — never forge a marker; a marker's mtime proves a touch, so read its CONTENTS against the current diff before trusting a gates:ok.
- A new source file can land as a git binary blob — verify `file` says "text" before committing.
- A registry/structural lint that reddens on a given day is usually pointing at that day's DELETION commit, not at itself — date the first red run, `git log -S <symbol>`, and never allowlist a constant to clear a coverage lint.
- "It's the tooling, not the app" is a CLAIM, not a default — name the mechanism and show the measurement before writing it. Two symptoms appearing together is not evidence of one cause; a workaround that FAILS is data — `pointer-events:none` not fixing a click means the listener is on an ANCESTOR (BUT-1837).
- Adding a CALLER changes the callee, even untouched — safe logs started leaking two raw uids once a new caller passed `direct_<uidA>_<uidB>`. Check a callee's logs, bounds and errors against the NEW caller's inputs; a doc ID can be PII no `hasOnly` sees, and a mutant that fails to COMPILE is not a red test (BUT-1822).
- An ARB edit rewrites the WHOLE file (a hook re-serialises the JSON), so `git diff` can't show whose changes are in it — compare KEY SETS against `git show HEAD:<file>` as JSON before staging any shared generated file. And re-run `flutter gen-l10n` afterwards: the generated file keeps the OLD string and `dart analyze` compiles it happily, so grep the generated file for the changed substring (BUT-1783/1693).
- A subagent's transcript file is NOT a liveness signal (0 bytes + stale mtime is normal mid-run — it flushes on completion); only the completion notification proves an agent finished. Wait in few LONG background sleeps, not many short holds.
- Anything you WRITE about code is an UNTESTED ASSERTION with a half-life — nothing exercises it, a reader trusts it most, and the change that falsifies it is usually YOURS one commit later. Before writing: grep the WHOLE tree including `__tests__`, diff against `git show HEAD:<file>` not memory, and for any "every/no/only" name what the quantifier ranges over. State the RULE, never the current mechanism, another comment's wording or position, or a line number — each breaks when you fix what it points at. A CORRECTION is as falsifiable as the claim it repairs (one paragraph shipped five false sentences in a row, each from the fix to the previous), so when a reviewer disproves one claim, re-check every other claim in the file. Decision records age the same way: grep the code before citing one, and supersede a stale entry rather than deleting it (BUT-1786/1819/1838/1903).
- A deploy that DELETES many Cloud Run services can leave its replacement `"state":"FAILED"` while `firebase deploy` exits clean and `functions:list` still shows it BY NAME — verify per-function `state` from `--json` after any deploy that removes services (BUT — 2026-08-03).
- "I read very little of what you reply" is a CONFIG bug first — grep the always-on setup (output styles, SessionStart plugins, stale model-tuning blocks) before apologising in prose; fix the mechanism (`~/.claude/output-styles/`) and delete the conflicting prose in the same edit.
- A verifier's RED COUNT fingerprints the bytes it READ — when a claimed defect contradicts the code, revert the fix and check whether the claimed signature reproduces exactly; a match proves the reporter sampled stale content (and indicts every other claim from that run), which beats "the claim is false".
- A model field that reaches Firestore is a RULES change too — `hasOnly` fails CLOSED in silence. A field added without touching `firestore.rules` once denied EVERY recipe write for three weeks, unnoticed. Grep `firestore.rules` for the validator in the SAME edit you add a field, and give every `hasOnly` allowlist a rules test (BUT-1482).
- A rules block that ATTESTS on a parent document must first establish WHERE and WHEN that parent is written — `get()`-checking a parent that materialises later (e.g. on first message) denies creation permanently. Shape: `attested || unclaimed` (parent names you, OR parent absent), proven against the writer's REAL WriteBatch (2026-08-12).
- "Not a live bug" is a claim about CALLERS, not about a nullable fallback — an unreachable default at one call site doesn't mean no path produces the bad value. Trace UP from the WRITE (grep the writing method, then each caller), never down from the field's own default (BUT-1849).
- A source edit made THROUGH another language inherits ITS escape rules: `\b` in a Python heredoc writes a literal BACKSPACE into a Dart comment, compiler-invisible, and it hit 3 source files AND the commit message in one go. Write `chr(92)+'b'`. `.github/workflows/text-integrity.yml` now sweeps the repo for control bytes, but no file sweep reaches a commit message (BUT-1901/1902, 2026-08-19).
- A hand-graded set is shaped by the SCREEN that fed it candidates — ask what that screen could not see; a second screen run over the finished set cannot score the first. Argue a borderline label from a WRITTEN criterion, never from the number it yields, publish the sensitivity, and never edit the measured input under a review that is reading it (BUT-1847).
- Python and Git Bash resolve `/tmp` to DIFFERENT dirs on Windows, so a Python writer plus a bash reader compares against a STALE file, and CRLF from `gcloud` makes `comm` see no overlap. Compare sets in ONE language, strip CR, `mktemp -d`. Complements that do not add up mean the INPUTS are wrong (2026-08-17).
- A ticket's stated harm can be REFUTED, not merely stale — trace the MECHANISM it cites, and when it is false ask what the ticket was written FROM: a wrong comment manufactures work that looks legitimate all the way to the commit gate. Fix the comment, rewrite the ticket with the measurement, file the real defect separately, and do NOT build the specified guard (BUT-1883).
- A shape-based redaction fails in BOTH directions and needs a test each way: a 20-28 char rule ate `PermissionDeniedException` (25 chars) itself, and `\b` counts `_` as a word char so a COMPOSITE id (`<uid>_2026-W34`, how a weekly plan is keyed) never matched. Keep non-data outside the masked span (type label, stack FRAMES — class names share the shape and web has no other sink), bound with `(?<![a-zA-Z0-9])` lookarounds, and ask what else in the string looks like the secret (BUT-1897).
- Every NUMBER, comparative ("most/every/only"), causal "because" and provenance DATE in a comment must be MEASURED before it is written — one sprint blocked four times and every block was a sentence, none was code ("the most throw sites": 20 vs 90; "roughly fifty": 173; a fabricated re-confirmation date). Run the count for every member of the set, not just the one you describe; prefer the RULE over the evidence, which rots.
- Moving a rule into a SHARED place raises three cross-file questions no single-file reviewer can answer: which other callers now apply it where they did not, which tests in UNTOUCHED files are now held up by the central rule rather than what they claim to pin, and did a widened pattern make ordering load-bearing. All three bit one PII change after six file-level passes. Run a whole-diff pass; repair a hollowed test with a case the CENTRAL rule cannot satisfy.
- A check run correctly against the WRONG OBJECT is indistinguishable from a clean bill of health — `git apply --check --3way` exits 0 while writing conflict markers (6 of 9 patches actually conflicted); a quoting check proved `secret-scan` innocent of an error whose real source is still unfound (the line was quoted 3 months before the symptom); a "deepest emission" was measured by a probe reaching only 1 of the function's 2 branches. Ask what the check's output RANGES OVER, not whether it ran: does this exit code distinguish the failure, is this the file the symptom came from (date the line), does the probe reach every branch. A verdict disagreeing with a symptom is usually measuring something adjacent (BUT-1921, 2026-08-26).
- A repo RULE file is an untested assertion too, and one that AUTO-LOADS has already shaped the code written under it — `ui-conventions.md` said `Semantics(label:)` suppresses the child `Text` when it CONCATENATES, so the notice announced itself twice and the first test agreed with the rule because it read the widget property instead of the rendered node. Assert against the artefact (`tester.getSemantics`), correct the rule, and scope the sweep of what it already produced. A false premise is likeliest to be RE-planted by the round removing it, and the repair text is where the next false sentence lands. Diff your edit against HEAD before describing it; never write a positional distance ("twenty lines up"), because the edit moving the text cannot type it right; and never describe your own diff in prose a later edit in the SAME change can falsify — a sentence citing `git show HEAD` is refuted by its own commit (BUT-1904/1953).
- A comment explaining WHY a test or guard is shaped as it is asserts what it CATCHES — a counterfactual about an unrun mutant, which reads as obviously true and is the claim that keeps returning wrong: eight false sentences in one batch, and one comment wrong in all THREE of its wordings. Write such a clause only after mutation-probing what it describes, else state what the code DOES and stop; after the SECOND failed repair of one sentence, DELETE the clause rather than attempt a third. Striking a numeral can BROADEN a claim — re-read what survives as a standalone sentence. And a REVIEWER's measurement is as falsifiable as a comment: one of the eight came from a critique's "the capped sweeps only exist for collectionGroup queries", folded in as a binding condition and refuted later by a counterexample in the same file — check a critique's quantifier before it becomes a plan condition, especially "X is the only Y" (BUT-1929/1800, 2026-08-27).
- A pipeline that has NEVER run hides every fault at once and fails serially — check `gh run list` before calling a failure a regression. One deploy path failed four times on four unrelated causes (missing Secret Manager role; `--force` required by a vetted `retry:true`; a 20 vCPU regional ceiling against 1 vCPU x maxScale 10, so ONE new revision reserves 10), and the fourth was its own smoke gate FAILING A DEPLOY THAT WORKED: `echo "$big" | grep -q` under `pipefail` takes its status from the writer SIGPIPE-killed when grep exits early, so which names read as missing depended on their position in the JSON. Treat any `| grep -q` under pipefail as a latent false negative, read a deploy's verdict off the RESOURCE not the exit code, and when a check disagrees with the artefact believe the artefact (BUT-1904 rollout).

## UI/UX

- A recurring report that reads its OWN previous output amplifies whatever framing it started with, one harmless step at a time: a competitor note scoped as "our strongest edge against THIS rival's false marketing" became "the claim Butlery's whole differentiation rests on" over several radar episodes, none of which re-read the product record that states the USP in its first line. Anchor every "what this product IS" sentence in the doc/code on EVERY run, never in the prior episode - a competitive contrast is a fact about the rival, not about what you are for - and when carrying a scoped finding forward, carry the scope: the qualifier is the first thing a summary drops.
- Heuristic/LLM-derived visible content (headings, tags, parsed amounts) ships WITH its correction UI in the MVP — "display now, correct later" is never a valid phasing.

## Language and Firebase gotchas

- Dart RegExp `\b` is ASCII-only — bound Swedish tokens with explicit lookarounds `(?<![a-zåäö0-9])`/`(?![a-zåäö0-9])`, and pin å/ä/ö-boundary cases in tests.
- Firestore `sum()`/`average()` with a filter on a DIFFERENT field needs a COMPOSITE index (filter field first, aggregated field included); `count()` doesn't. In-memory fakes can't catch it — assert the declared index config in a test.
- A FAILED_PRECONDITION's `create_composite` token base64url-decodes to Firestore's OWN index spec — decode it before trusting a description of the cause. `orderBy(documentId(), 'desc')` needs a declared `__name__ DESCENDING` index; the retry then says "index is currently building" — poll, don't re-fix.
- A boundary/heuristic/attribution bug usually has a TWIN CLASS — grep sibling classes by NAME (not path) and trace which one the view actually calls; a legacy sibling is as likely to be live. Fix both in one commit or delete the dead one (BUT-1691, BUT-1697/1716).
- A harness picking between two on-disk shapes for the same fact must choose on the property that decides TRUTH (which is `verified`), never on which FILE EXISTS — existence is a side effect of production, and the loser drops silently (BUT — corpus split eval, 2026-08-05).
- A wrong-path Firestore read is a bug CLASS — wrong collection, wrong field, or a filter on a field that doesn't exist all look like "matches zero" and the analyzer sees none of them. Grep the CONSTANT for every reader AND writer, and check each against `firestore.rules`: no `match` block means denied, not undocumented (BUT-1724).
- "Affected users" is a CLAIM WITH A TIMESTAMP — a bug's shape can suggest a population that dies to one timestamp check. Date the window at both ends and check live status before any sentence about who is affected (BUT-1846).
- A rule bounding a field's VALUE does not bound a denormalised COPY of it on another collection — a deny-list there won't name the field, so the copy stays writable. And "how long does the bad value persist" is a claim about EVERY writer, server trigger AND client repo alike: a client that merge-sets without comparing makes it permanent (BUT-1903).
- A claim can be true per verb, caller, purpose or fixture and false universally — that qualifier is where a repaired comment goes wrong the second time (BUT-1838).
- A config artefact in the wrong SHAPE is dead SILENTLY and forever — a flat `.claude/skills/<name>.md` never loads (only `<name>/SKILL.md` or `.claude/commands/<name>.md` do), and a hook whose interpreter is missing fails exactly like one that decided "allow". 14 skills and a force-push guard were dead ~9 months while CLAUDE.md, four rules files and a hook all named them. Existence is not liveness: proof is a non-zero `skillUsage` entry, a session-listing hit, or a recorded hook decision — and `.claude/settings.json` is not the full hook picture, since enabled plugins add their own from `<plugin>/hooks/hooks.json` (2026-08-22).
- Read the first three lines of any config/data file before editing it — a "Generated by … do not hand-edit" banner means your fix has a fuse (here: the weekly `/janitor` regenerates it). Fix the SOURCE, re-run the generator, then DIFF and say which changes are yours and which were already-stale drift. And check what a derived glob would newly claim: repointing one Evidence token would have handed one role another role's 22 files — a new bug created by the repair (2026-08-22).
- A guard that stops a bulk sync undoing one kind of human decision is evidence you saw the hazard — and exactly why nobody checks the OTHER direction. `departedUserIds` protected an explicit REMOVAL from the meal-vote roster sync while the same sync silently deleted an explicit ADDITION an admin made elsewhere, re-writing "X har lämnat gruppen" after every re-invite; five per-file passes approved it, only the whole-diff pass saw it. Name both directions in the same edit, and fix it with a POSITIVE set of what the mechanism itself seated — never a heuristic on a field a safety check reads (BUT-1856).
- ONE new export falsified eight counting sentences across five files in one commit ("the three callables", "All FOUR are pinned", "70 gen2 services", "all 71 endpoints", "the two raw uids") — every one true when written, none asserted, none reddening. Strike the numeral instead of re-counting, sweep the WHOLE file (a header fix reads as done while three more sit in the body), and where the count is load-bearing replace the prose with a test that DERIVES it (BUT-1856).
- A count that describes a file you are still editing cannot be TYPED — the `ACCEPTED_LARGE_FILES` row was written three times in one change and was wrong all three (774 vs 801, 1148 vs 1165, 1165 vs 1176), each correct when measured and falsified minutes later by my own next edit. Recompute it from `wc -l` in the SAME call that stages and commits: any figure measuring another file in the same commit is a derived value, and a derived value a human types is wrong (BUT-1911).
- A CLI's output format is a PLATFORM variable: GNU grep moved "binary file matches" from stdout to stderr in 3.5, so a guard running `2>/dev/null` stayed green on the dev machine's grep 3.0 and silently stopped enforcing on CI's 3.11 — for its whole life, not just since the rewrite that exposed it. Reproduce a tool's output on the TARGET platform before parsing it, key the parse on what the message cannot lose (a missing `:<line>:`, not its wording or stream), and treat any `2>/dev/null` in a guard as a written claim that the stream holds nothing it needs (BUT-1894).
- The paragraph written to BE the correction is where the next false sentences land — round after round in one change, each inside text authored as the fix, and a strike in the header left the same claim REWORDED 100 lines lower in the body. The lesson entry recording this shipped its own stale COUNT of them, caught in the same commit. Two shapes recur. (1) A pointer ("the test that pins this") is a QUANTIFIED claim: it must resolve for every symbol the sentence ranges over — naming two constructors and one test left the group half unguarded, and its rules test would have kept passing while pinning a hazard that no longer existed. Close the gap rather than scope the sentence; a caveat documents the hole forever. (2) Narrating what the OLD comments believed re-plants the inversion you are removing, as history, and is a claim about ticket text no test can hold. Also: attribution of a DENY is a measurement, not a structural argument — "the other conjuncts are satisfied" was wrong about a fixture that carried the owner's own uid; removing the conjunct and watching the test stay green was right (BUT-1961/1928, 2026-08-27).
- A DORMANT assertion protects nothing, and every sentence written beside it is unfalsifiable rather than true: a blanket `FlutterError.onError` made every golden mismatch report a PASS, and while it did, the helper claimed the PNGs were "deterministic across platforms" — the moment the comparison went live, 7 of 8 differed on ubuntu and 6 of 7 on macOS. The comment written to JUSTIFY the fix then named the verify skill and the commit gate as the remaining safety net; neither runs a Flutter test. Re-check every claim written while a check was silenced, open a mechanism's config before naming it as the guard, and never move a measured count to a neighbouring set — the phrase that fit 7 failures was false on 8 comparisons (BUT-1931).
- Never end a reply with a future action in the PRESENT tense — the turn terminates on that sentence and nothing runs. Twice in one session ("kör om granskarna", "jag stagar om och kör…") the work was announced and never done, and the user cannot tell an announced action from a completed one because both are written identically. Do the action IN the turn and report it after; if it genuinely cannot run yet, write "nästa steg:" and never a present-tense verb. Same class as a false code comment — an assertion nobody measured — except the reader is the founder, who cannot check it against the code (Malin, 2026-08-29).
- Before designing a new attribution field's STORAGE or its erasure, grep every construction site of the thing it attributes and ask whether any path can make it differ from a field that already exists: a poll option's proposer is always the poll's `creatorId`, so the new field would have been a second copy of a known fact AND a uid inside an array-of-maps, which Firestore cannot query and the deletion cascade therefore cannot reach (the bug class BUT-1832/1835 already paid to fix by moving `voterIds` to a subcollection). The check is minutes; the erasure design it removes is a day. A finding that dissolves this way is still a good finding — it forced the question. And where two variables must hold the same value on the only live path, pass them separately anyway and say they are equal TODAY, measured, rather than implying a test proves the distinction (BUT-1971, 2026-08-30).
- A gate reviewing a staged diff must see a FROZEN index: editing while it reads makes it report findings you already fixed, forces you into disproving a reviewer (the position where a real finding gets waved away as "already fixed"), and produces the header-fixed/body-stale contradiction as a side effect — one gate traced a finding directly to my mid-review edit. Batch fixes, re-stage once, re-brief; kill the agent rather than let it grade bytes that will not ship (BUT-1957, 2026-09-02).
- Ten false sentences in one change, and ALL TEN were inside text written as a repair — none in a first draft. A correction is written in the state of mind least suited to writing one: just shown you were wrong about X, you write confidently about X's neighbourhood, unmeasured. "No third party appears in these rows" came from checking the writers' FIELD LISTS when the name arrives in a field's VALUE one call away; "deletes the single document by id" was written inside the commit that changed it to sweep the collection; two counts were both wrong and one was refuted by its own commit. Strike rather than reword, grep the WHOLE diff for other wordings of the fact you just corrected, and never write a count (BUT-1957, 2026-09-02).
