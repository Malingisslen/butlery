# Lessons Digest — testing

Lessons that only bind while writing or running tests. Counted by the same drift tripwire
as the core digest (`knowledge.digestFiles`), so these are as in-force as any other lesson —
they simply do not load in sessions that never open a test file.

- Eval input must match PRODUCTION input, not the cheapest-to-label input.
- Red CI on an unrelated test = suspect a pre-existing flake; fix the flake at root (seed the RNG) — never rerun-until-green.
- Chronic-red CI disarms safety-gate tests silently — triage any always-red job to zero promptly, and after moving a definition, grep tests for hardcoded paths/regexes aimed at the old site.
- `architecture_test.dart` guards are NOT in `dart analyze` — analyze-clean ≠ CI-green for `lib/widgets/`.
- Adding a named param to a mocked service silently un-matches every old mocktail stub — update the stubs.
- cloud_firestore's FieldValue caches the platform factory statically — fake batches can throw subtype errors.
- Lexicon-dependent tests: assert the premise, and watch NFC vs NFD normalization on å/ä/ö.
- real-time-guard matches the literal `DateTime.now()` even inside comments.
- After changing a class's constructor, run its EXISTING test suites — not just the new test you wrote.
- A DI cap/gate seam defaulting to a real-Firestore resolver fails CLOSED in ts-node CF unit tests (no Firebase app) and silently diverts control flow on every path that reaches it — inject it to `async () => true` in those tests (mirror `makeOcrSeams`); if a sibling suite is red, STASH your diff first to check it wasn't already red on main, then fix at root.
- A golden/corpus suite is TWO files — the corpus JSON and the runner's `_expectedPassing` id snapshot; extend both in one edit. A green golden run proves only the LISTED ids behave, so grep the corpus for the literal string an acceptance criterion names before claiming it's covered (BUT-1666 went 17/17 green with all three named collision strings absent and still misclassified).
- `FakeFirebaseFirestore.runTransaction` is a NO-OP passthrough (handler called once, writes immediate, `SetOptions`/`timeout`/`maxAttempts` dropped, no isolation/abort/retry) — a two-writer test there LOSES one edit, i.e. it contradicts production rather than under-proving it; `merge:true` is dropped and `GetOptions(source:cache)` is ignored (real Firestore THROWS `unavailable` on a cache miss). Never let a fake-backed test's name or comment claim atomicity; put that on the emulator lane, and verify the lane actually runs in CI before counting it (BUT-1665/BUT-1695). The fake also DROPS a `FieldValue` sentinel inside a transactional merge-set (an `arrayUnion` comes back as just the new value) — compute the union explicitly from the snapshot the transaction already holds. And the emulator lane cannot simply be switched on: `--dart-define=USE_EMULATOR=true` under plain `flutter test` makes `Firebase.initializeApp` throw a channel `PlatformException` (no plugin channels in the Dart-only host) — it needs an `integration_test` host or a pure-Dart client (BUT-1730).
- Auditing a mature test suite means auditing DISCOVERY, not adding test types — every runner that decides what to run from a HAND-TYPED list (npm `test:*` script names, a workflow `paths:` filter) is a silent-drift hole; prove orphan counts by script, then guard the list. Rank by blast radius of the check going dark.
- A comment MAPPING assertions to the edits they catch is itself an untested assertion — mine was inverted while the probe output on screen said otherwise, and following it would have deleted the only guard against one edit (the survivor passes VACUOUSLY there). Re-read the probe output against the sentence, and when two assertions guard one invariant, state which is vacuous without the other.
- A test written to pin a fix is a HYPOTHESIS until you revert the fix and watch YOUR test redden (then restore, md5-verified). Three ways one passes vacuously, all hit in one sprint: a tautology over the implementation (assert key ABSENCE, not value non-nullness, when the builder filters keys); a fixture answered by an EARLIER branch (a digit reaches `RegExp(r'\d')` first; a factory that stamps every field makes an "unstamped" case impossible — check the branches ABOVE, not only beside); and a premise the fake cannot stage (`fake_cloud_firestore.update()` DEEP-MERGES nested maps, and `GetOptions(source:)` is ignored, so cache-vs-server divergence must come from the mutator, never the stored doc).

- Two Firestore deny tests cannot be told apart by their `PERMISSION_DENIED` text — the evaluation error fingerprints the RULE LINE, not the actor, so SSL22 and SSL40 print byte-identical verdicts. Prove non-vacuity with a FAIL-CLOSED control (same doc/id/actor/payload but the actor seated → must ALLOW) plus a DISCRIMINATING MUTATION (the suspected duplicate's branch grants → the new test flips, its neighbour stays denied), and send the REAL production payload at least once.

- Rerouting a call through a shared helper inherits the helper's DEPENDENCIES, and a test double written for the old ones is now incomplete, not merely old — `LinkifiedText` routed through `openExternalLink` gained a `canLaunchUrl` call the recording fake did not implement, and ordinary comment links stopped opening. It survived six review passes because every test run named the folders I had EDITED and the broken test lived elsewhere. Before calling a reroute "defence in depth, behaviour unchanged", diff the helper's calls against the old line, then run the suites found by grepping the DEPENDENCY's name across `test/`. And when a test only passes once you EXTEND a double, ask whether the new dependency belongs there at all before extending it — here it did not (`canLaunchUrl` answers a permission question, and iOS declares no `LSApplicationQueriesSchemes`), so dropping it left the double byte-identical to HEAD. Adding a `catch` in the same commit can convert the new failure into silence — add it after the suite is green, or run once without it (BUT-1819, 2026-08-10).

- A rules branch keyed on `parentDoc() == null` treats DESTROYED as NOT-YET-CREATED — the two states are indistinguishable to Firestore rules, so a permissive bootstrap branch silently re-opens for every conversation anyone deletes. Before shipping one, enumerate EVERY deleter of the parent (the client `allow delete` AND each CF), because the fix can only live in code: here the eviction CF deletes the conversation when the group collapses, which is the same CF whose missing roster cleanup the branch was written to contain. Pin the deleted-parent state as its own fixture, and seed the subcollection the production writer really seeds — a cleanup assertion over an empty collection passes for free (2026-08-12).
- Compiler EXHAUSTIVENESS is a proof about the SET, not about the MAPPING or the WIRING. Turning a stringly-typed field into an enum made the SDK's one-match assert unreachable — the fix working — and simultaneously made my own `takeException` assertion unfailable under a comment calling it "the primary proof". The `default`-less switch proved every value gets A label; nothing proved the RIGHT one, no test read either label, and swapping the two arms compiled green while a subscriber would see the opposite word on screen. Dropping the value from the copy-constructor call stayed green too — nothing tapped the control. When a type change removes a failure mode, ask what the old assertion caught and what still catches it: pin the item list against `.values`, and tap the control and capture the save (BUT-1846, 2026-08-14).

- A test written to be DELETED must ship with the assertion that outlives it. A defect-documenting test labelled "delete this when BUT-1858 lands" held the suite's only assertion on `PantryItem.unit`, so the day the fix arrives and the test goes, an "always writes 'st'" regression would pass unnoticed. Ask of every temporary test what goes unguarded on the day it is removed, and pin that on the happy path in the same edit. Its comment is load-bearing too: the reachability sentence beside it was false in the same way the production comment's was (BUT-1849, 2026-08-15).

- A mutation probe is a WRITE to real code and your own script is the instrument — back up first, restore from a `finally` AND from SIGINT/SIGTERM/SIGHUP/SIGBREAK, then assert bytes are identical (a harness timeout once killed a probe mid-restore and the suite stayed GREEN with the mutant live). Scraping a total from tool output: anchor on a unique prefix or take the LAST match — a nested sub-suite's "N checks passed" reads exactly like the outer one.
- A test fixture must CONTAIN the pattern it claims to guard, and clear every length/shape precondition on the path it exercises — three vacuous tests once shipped as coverage ('paprika.' has no "ca" in it; another check was too short to reach the guarded branch). Always mutation-test a negative assertion.
- An SDK's "unset" can be a sentinel OBJECT, not null — firebase-functions leaves `maxInstances` as an object whose `toJSON` renders as `null`, so `JSON.stringify` prints "null", `'k' in obj` is true, and `v == null` is FALSE. A presence check written as `== null` then passes under a mutant that deleted the option from all 70 functions. Test the SHAPE you require (`typeof x === "number"`), type the field `unknown` so a narrow type can't invite the dead check, and treat a mutant reddening a DIFFERENT assertion than predicted as the vacuity showing itself — probe the raw value then (2026-08-17).
- Judging what a PHOTOGRAPH shows by reading its OCR text measures the OCR, not the page — type size, column structure, frame crop, and objects in the same shot are invisible in the string. Open the images before grading or recording a verdict. A GROUND TRUTH graded the same way inherits the blindness (BUT-1816).

- A comment calling a comparator or guard "load-bearing" is an untested assertion until a fixture sits EXACTLY on the boundary — `<` vs `<=` passed 19/19 and 9/9 because every fixture sat clear of it (19 being the suite as it then stood; the case ADDED to kill it makes 20, so today's total would name a suite the mutant does NOT pass). A FAST PATH upstream is what makes that easy to miss: it catches the boundary case first, so the mutant survives AND the stated failure mode is not the one a flip produces. Trace what short-circuits above the check before writing why it matters (2026-08-19).

- A test can go RED with no commit behind it — a literal past date beside a TTL is a time bomb (`isExpired` reads `clock.now()`), so date the first red RUN and ask whether any commit even lands in the window before reading diffs. Derive presence fixtures from the clock; keep absolute instants for boundary tests that pin one inside `withClock` (BUT-1905).
- A rules TIGHTENING makes every older DENY test on that path vacuous and nothing reddens: after one, re-attribute each DENY to the single-variable ALLOW control it differs from — two differing variables means over-determined, proving nothing. Two live cases in one file; deleting `isAgeCompliant()` from `recipe_comments` left the whole suite green, and those tests were its only guard. Emulator output cannot tell you — every deny prints an interchangeable `PERMISSION_DENIED` naming a rule LINE, not a reason (BUT-1905).
- Over-determined is NOT short-circuited, and conjunct order is a PER-COLLECTION fact — `recipe_comments` reads age then maturity, `messages` reads membership then maturity then age, so a sentence about which check denied first is true for one and false for the other. State the property the test depends on, never the order (BUT-1905).
- A probe that deletes only a helper's CALL SITES does not compile: `noUnusedLocals` makes ts-node abort on TS6133 before any test runs, and that exit code reads exactly like a red assertion. Delete the declaration too, or mutate the fixture data (BUT-1905).
- A formula copied into its own test proves the test agrees with itself — move it somewhere importable and import it. Doing so here immediately reddened: the delegate had been reading `MediaQuery` from a context ABOVE the test's own override, so every "2x" case had measured a 1x tile (BUT-1895).
- A mutation probe's RESTORE can silently revert an unrelated fix made after its backup was taken: take the backup immediately before the mutation, never reuse one across edits, and `git diff` the probed file afterwards. Verify a REMOVAL against `git show :<path>` — a worktree fix that never reached the index looks identical to one that did.
- An invisible codepoint makes correct code read as broken — byte-check a suspicious bound (`cat -A`, `grep -P`) against real data before trusting a visual read. When a ticket claims a guard test is missing, MUTATION-TEST the existing suite first — the alarm often already exists (BUT-1690).
- Two samples cannot attribute a NONDETERMINISTIC failure: establish determinism first (does it fail in isolation? every time?), then run N>=5 per tree and compare RATES. A strict `isAfter` between two wall-clock stamps is a same-tick coin flip — recognisable before running anything.
- A `Fake` fixture inside a FAIL-OPEN catch makes the test measure the CATCH: `copyWith` on a `Fake` throws, the catch swallows it, and the service serves the unfiltered page — indistinguishable from the feature never running. Use the real model type for anything production calls a method on, and never read a fail-open/fail-closed pair as evidence for one cause without enumerating the others. Same trap next door: `TestServiceLocator.initialize()` SKIPS the production `ServiceLocator`, so `tryGet<T>()` returns null for everything until the group stands up its own `ServiceLocator.initialize(DIContainer())` — the service then never finds the collaborator at all (BUT-1909, 2026-08-22).
- A comment that COUNTS the tests below it has an insertion seam, and the next legitimate test is what breaks it — "only the X case discriminates; the other two are controls" went false the round after it was written, when a review finding added a fourth. Name the LITERALS instead; a literal survives an insert. Distinct from ordinary number-rot: the count was correct when written and was falsified by your own later work (BUT-1910, 2026-08-22).
- A widget test that finds NOTHING may be looking at an unbuilt widget, not a wrong finder — a lazy `ListView` body builds a form field only when scrolled near, so count the widgets of that TYPE in the tree before doubting the label, and put `scrollUntilVisible` in a named helper. A field seeded with `initialValue` also has a NULL `TextFormField.controller`: read its text off the descendant `EditableText` (BUT-1910, 2026-08-22).
- One pump per test when measuring a LAYOUT error: `pumpWidget` reuses the element tree, so a search that raises a candidate height inside one `testWidgets` stops at the first candidate and reports the same number for every input. A suspiciously CONSTANT answer across inputs that should differ is the instrument, not the finding — pump once with generous constraints and read the geometry off the tree (BUT-1911).
- When a fix removes a widget's ability to SHRINK, the tests that break were asserting the old contract by accident: three green cases had handed the recipe grid card a box it could not hold and passed only because the photo gave up its height. Fix the harness to the widget's real usage and say so, rather than capping the widget to keep an unrealistic box green (BUT-1911).
- A service behind an `executeServiceOperation`-style wrapper can pass a stubbed-repo test WITHOUT the repo: the wrapper's auth pre-flight reads the PRODUCTION `ServiceLocator`, so without `setupUnitWithProductionLocator` the closure never runs and the assertion matches the fallback's shape. Assert the stubbed method was CALLED, not that the result shape matches, and sweep the siblings — the missing harness is a property of the wrapper, not the feature (BUT-1937, 2026-08-23).
- A mutation probe can certify a LIVE mutant as covered: `flutter test` serves a stale incremental kernel after the rapid file swaps a probe loop makes, and one probe reported a live mutant GREEN while two runs of the UNMODIFIED file went red. `rm -rf .dart_tool/flutter_build` between the edit and the run makes results reproduce. The error is ONE-DIRECTIONAL — a RED probe is trustworthy (a stale kernel of correct code cannot manufacture a failure), a GREEN one is a hypothesis. One "this guard is unpinned" conclusion was falsified this way minutes later by a second measurement. Never write "unpinned" from a green probe alone (BUT-1971, 2026-08-29).
