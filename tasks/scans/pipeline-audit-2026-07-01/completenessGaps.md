# Audit blind spots (completeness critique)

## 1. [high/safety] Menu generation ignores user allergen overrides and the coverage/distrust guards the list filter applies — VERIFIED
The recipe-list allergen filter is careful: it refuses to trust a result that `needsRetagging`, refuses coverage < 100%, and applies the user's manual tag corrections via `TagEditingService.getEffectiveAllergenStatus` (`lib/viewmodels/recipe_list_viewmodel.dart:975-1006`). The menu generator does none of this: both `_filterByPrefs` and `_filterByAllergenPreferences` read raw `tagResult.getAllergenStatus(...)` with no override lookup, no coverage check, no needsRetagging check (`lib/viewmodels/menu/menu_generator.dart:209-218` and `:246-264`). Failure scenario: user manually corrects "this actually contains gluten" (the only correction channel that exists — audit confirmed overrides are otherwise display-only), then generates a weekly menu → the recipe is still served as safe. Also, a partial/low-coverage TagResult that the list would distrust is trusted by the menu. This is distinct from the confirmed "household filtering is dead code" finding: even the *live* single-user path has weaker safety semantics than browsing. Look: diff the two filter implementations above; check whether `TagEditingService` is reachable from `MenuGenerator` at all.

## 2. [high/flow+cost] Retagging/invalidation subsystem was never mapped — remote tag-config changes never invalidate existing tags
`RetaggingScheduler` (`lib/services/tagging/retagging_scheduler.dart`) is a whole unmapped subsystem: it scans all recipes 5s after every app start and every 24h, retagging up to 100/session. Two consequences the audit missed:
- **Invalidation keys only on a code constant.** `TagResult.needsRetagging` returns true only when `generatorVersion != kTagGeneratorVersion` (`lib/models/tagging/tag_result.dart:762-770`; constant `'2.1.0'` at `lib/services/tagging/tag_generator.dart:17`). The Firebase-remote tag config (`lib/services/tagging/tag_config_service.dart`, `lib/models/tagging/firebase_tag_config.dart`) can change allergen/dietary rules WITHOUT any version bump → every already-tagged recipe keeps verdicts computed under the old rules, forever. There is no "config revision" stamped into TagResult and no retag trigger on config change.
- **The converse is a fleet-wide cost bomb:** bumping `kTagGeneratorVersion` makes every recipe on every device `needsRetagging` → every user's client re-runs the full tagging pipeline over their whole library (100/session cap, ingredient lookups, potential LLM-adjacent work). No server-side/batch retag path exists, and cross-user global-cache entries are never retagged (compounds the confirmed stale-cache finding).

## 3. [high/safety+SPOF] Ingredient master-data governance: three writers, full-overwrite adds, and no gate between a Google-Sheet edit and production allergen verdicts
The Sheet→Firestore pipeline was named but never examined. Reality: **three independent writers** to the global `ingredients` collection — the Cloud Function sync (`functions/src/admin/sync-ingredients.ts`), a *duplicate* standalone admin tool (`tools/sync_ingredients.dart`, 427 lines of parallel diff/sync logic that can drift from the CF), and the alias-learning CF writing `learnedAliasesSv` (`functions/src/analytics/analyze-corrections.ts:262-294`). Issues:
- The `toAdd` path is `batch.set` full overwrite (`functions/src/admin/sync-ingredients.ts:588`, `tools/sync_ingredients.dart:141`) — a re-added/ID-recycled ingredient silently wipes its learned aliases (updates preserve them; adds don't).
- **No validation, eval, or review gate**: a wrong cell in the Sheet's allergen column propagates to every user's allergen verdicts on next sync. Given finding #2, recipes tagged *before* the bad sync keep old verdicts and recipes tagged *after* get poisoned ones — silently inconsistent, and no rollback/diff-report mechanism was audited. This collection is the single point of failure of the entire allergen chain (client rules correctly block direct writes, `firestore.rules:2202-2205`, so the writers above are the whole attack/error surface).

## 4. [medium/flow] TagResult schema migration is read-time-only and the serialization layer went unmapped
`TagResult._migrateSchema` migrates V0→V2 in memory on every read and never writes back (`lib/models/tagging/tag_result.dart:485-519`); old-format docs live forever and every future schema change compounds the in-memory migration matrix. The broader recipe model/serialization layer (`lib/models/recipe_unified.dart`, `lib/models/tagging/*`, the BUT-648 lazy-compat `schemaVersion` convention in `lib/repositories/CLAUDE.md`) carries the USP's persisted state — including cross-user global-cache entries that ship one user's TagResult (allergen verdicts included) to other users — and had zero audit coverage on round-trip/migration correctness.

## 5. [medium/learning] The measurement *consumer* is outside the audited tree
The confirmed parse-events findings audit only the producer side. The admin dashboard that reads `parse_events` (Importhälsa/Parsing-detaljer tabs) is a **separate app** (live at butlery-admin.web.app, separate codebase per project memory `project_admin_dashboard.md`). Nothing ties the event schema written here to the queries the dashboard runs — a field rename in the Flutter producer breaks parse-health monitoring silently, and the audit could not have seen it. Look: schema of writes in the parse-event logger vs the admin repo's queries; also `functions/src/events/log-parse-correction.ts`.

## 6. [low/testing] Retagging scheduler + tag-editing/override subsystem have no audit coverage at all
Neither `retagging_scheduler.dart` nor `tag_editing_service.dart` (the user-override layer that turns out to be safety-load-bearing per #1) appears in the mapped subsystem list or the test inventory. The override layer is the only human check on the auto-tagger; whether its persistence, precedence, and consumption points are tested is unknown. Look: `lib/services/tagging/tag_editing_service.dart` and `test/unit/services/tagging/`.

Not flagged (checked and OK): Firestore rules on global `ingredients` (client write denied); alias-index diacritic normalization exists (`lib/repositories/firebase/firebase_ingredient_repository.dart:242+`); sheet-sync `update` path preserves `learnedAliasesSv`.
