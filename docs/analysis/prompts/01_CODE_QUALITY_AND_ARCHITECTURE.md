# Code Quality & Architecture Analysis

## Analyst

Claude (Opus 4.7) -- comprehensive codebase analysis agent.

## Mission

Perform a forensic-level code quality investigation of the Butlery Flutter codebase. The goal is to achieve industry gold standard quality suitable for production deployment with zero critical bugs, optimal maintainability, and professional-grade code health.

This is not a superficial review. This is a deep investigation across 8 weighted dimensions of code quality, totaling 100 points.

## TWO-PHASE APPROACH

### Phase 1: Investigation & Documentation (THIS PHASE)

**CRITICAL**: Document everything, change nothing.
- Investigate all aspects systematically
- Document findings with file:line references
- Classify issues by severity (Critical/High/Medium/Low)
- Provide effort estimates for each issue
- **ZERO code changes made**
- **ZERO files created or modified**
- Output: Complete findings report ready for Phase 2 planning

### Phase 2: Smart Remediation Planning (AFTER Phase 1 Complete)

- Review ALL Phase 1 findings together
- Prioritize by impact, effort, and dependencies
- Group related issues for efficient batch fixing
- Create optimized fix sequence to minimize breaking changes
- Generate sprint-structured remediation plan

**DO NOT START PHASE 2 UNTIL PHASE 1 IS COMPLETE**

## Generated Files: Exclude from Analysis

The following file patterns are auto-generated and must be excluded from code quality analysis:

- `*.g.dart` - Build runner generated files (e.g., `app_database.g.dart`: 3,271 lines)
- `*.freezed.dart` - Freezed generated files
- `app_localizations.dart` and locale-specific files (`app_localizations_sv.dart`, `app_localizations_en.dart`) - Generated by Flutter l10n

When reporting file counts and LOC metrics, always provide two numbers: total (including generated) and hand-written only (excluding generated).

## Investigation Framework: 8 Dimensions (100 Points Total)

### Dimension 1: Architecture Compliance (20 points)

**Investigation Scope**: MVVM pattern adherence, repository pattern compliance, dependency injection correctness, and service layering.

**Specific Investigation Tasks:**

1. **MVVM Pattern Adherence**
   Verify the architecture follows Views -> ViewModels -> Services -> Repositories -> Firebase consistently.
   ```
   Search patterns:
   - Views importing repositories directly (skip ViewModel layer)
   - ViewModels importing Firebase packages directly (skip Service/Repository layers)
   - Services calling Firebase APIs directly (skip Repository layer)
   ```
   - Document every layer violation with file:line reference
   - Assess impact on testability and maintainability

2. **Repository Pattern Compliance**
   Find all direct Firebase instance usage -- these bypass the repository pattern.
   ```
   Search: FirebaseFirestore.instance
   Search: FirebaseAuth.instance
   Search: FirebaseStorage.instance
   Search: FirebaseMessaging.instance
   KNOWN: 17 files with direct Firebase instance usage
   ```
   - Verify each occurrence violates the repository pattern (some may be in repository files themselves, which is correct)
   - Assess impact on testability
   - Generate refactoring plan with effort estimates

3. **Dependency Injection Correctness**
   ```
   Verify:
   - All services accessed via ServiceLocator.get<T>()
   - No direct class instantiation of services in widgets/ViewModels
   - DI modules organized correctly (Core, Content, Social, Messaging, Collaboration, Performance, UI)
   - Constructor injection used in DI modules, ServiceLocator in widgets/ViewModels
   - No circular dependencies between DI modules
   ```
   - Document any incorrect DI patterns
   - Check for circular dependency risks

4. **Unified Service Layering**
   Verify services expose sub-services via `.personal`, `.social`, `.realtime`, `.share` where applicable.
   ```dart
   // Correct pattern:
   await recipeService.personal.createRecipe(...);
   await recipeService.social.shareWithFriends(...);
   final stream = recipeService.realtime.watchRecipe(...);
   ```
   - Find services that should use layered architecture but don't
   - Document inconsistencies

5. **Data Source Discipline**
   ```
   CRITICAL DATA SOURCE RULE:
   - UserService.currentUserProfile -> complete user data (settings, avatar, social)
   - PermissionService.currentUser -> basic auth/permission checks only
   - NEVER mix these (causes settings not persisting)

   Search: Files importing both UserService and PermissionService
   Verify: Each file uses the correct source for its purpose
   ```
   - Document every data source confusion with severity
   - These bugs are subtle and cause settings persistence failures

6. **Facade Pattern for Large Models**
   Check that large models use delegation (e.g., Recipe -> RecipeOperations, RecipeFactory, RecipeSerialization).
   - Find models with >500 lines that lack facade decomposition
   - Check ACCEPTED_LARGE_FILES.md before flagging

7. **setState() in ViewModels**
   ```
   Search: setState() calls in files under lib/viewmodels/
   KNOWN: 2 files
   - realtime_menu_viewmodel.dart
   - realtime_menu/realtime_menu_state.dart
   Should use ChangeNotifier/StateNotifierMixin instead
   ```
   - Verify these are the only occurrences
   - Assess migration complexity

**Output Required:**
- List of all architectural violations with file:line references
- Severity classification for each (Critical/High/Medium/Low)
- Refactoring effort estimates (hours/days)
- Migration strategy for each violation category

**Current Status:** 1,617 try-catch blocks across 361 files.

**Specific Investigation Tasks:**

1. **Error Handling Completeness**
   ```

   - Silent failures (empty catch blocks): catch (e) {}
   - Catch blocks that only log but don't surface errors
   - Generic catch (e) without proper error classification
   - Missing error handling on Future chains (.then() without .catchError())
   ```
   - Document each gap with file:line reference
   - Classify by data loss risk

2. **Network Resilience**
   ```
   Verify:
   - Retry logic on network operations (max 3 retries via ErrorHandlingMixin)
   - Timeout handling on all Firebase operations
   - Offline support / Firestore offline persistence
   - Queued retry for failed operations
   - DNS-aware error handling (executeFirebaseOperationWithDNSResilience)
   ```
   - Document operations without retry logic
   - Assess offline mode capabilities

3. **User Error Communication**
   ```
   Audit:
   - Error messages shown to users (technical jargon vs user-friendly)
   - DialogService usage for error display
   - Empty state messaging quality
   - Loading state indicators during operations

   Anti-patterns:
   - throw Exception('NullPointerException in...')  // Technical jargon
   - catch (e) { print(e); }  // No user notification
   - 'Error occurred'  // Not actionable
   ```
   - Find all user-facing error messages
   - Classify: actionable vs vague vs technical

4. **Graceful Degradation**
   ```
   Check:
   - Features that degrade gracefully on failure
   - Fallback mechanisms for failed operations
   - Cache-first patterns for network failures
   - Partial data display when full data unavailable
   ```

5. **Input Validation**
   ```
   Find all user input points:
   - Form text fields (recipe title, ingredients, instructions)
   - Numeric inputs (portions, cooking time, amounts)
   - File uploads (images)

   Verify:
   - ValidationUtils usage on all input fields
   - Boundary value handling (empty, null, very long, negative numbers)
   - Special character sanitization
   - File type and size validation

   Search for:
   - TextFormField without validator
   - Numeric parsing without error handling (int.parse without try-catch)
   - User input passed directly to queries without sanitization
   ```

6. **Data Integrity Under Error Conditions**
   ```
   Scenarios:
   - Partial write (operation interrupted mid-save)
   - Invalid data types in Firestore documents
   - Missing required fields in incoming data
   - Orphaned references (recipe references deleted user)
   ```

   - Document data corruption risks

   ```
   - // ===== SECTION =====
   - // ---- Helper Methods ----
   - /****************************/

   Swedish comments (should be English):
   - Search for Swedish words in comments (inte, och, om, denna, etc.)

   Complex logic WITHOUT explanation (missing WHY):

   - Magic numbers without context
   ```

2. **Commented-Out Code**


2. **Code Smells**
   ```

   - Feature envy (class extensively using another class's data)
   - Primitive obsession (using String/int where a value object would be clearer)
   - Data clumps (groups of parameters that always appear together)
   - Shotgun surgery (one change requires modifications across many files)

   Tool: DCM provides 475+ customizable lint rules for automated detection
   ```
   - Catalog code smells by category
   - Prioritize by refactoring impact

3. **Magic Numbers & Strings**
   ```
   Search for:

   - Hard-coded string literals (especially repeated ones)
   - Hard-coded durations, timeouts, sizes
   - Hard-coded Firebase collection names (should be constants)
   - Hard-coded color values (should reference theme)

   Exceptions (acceptable):
   - 0, 1, -1 in common patterns
   - Standard HTTP status codes in context
   - Obvious mathematical constants
   ```
   - Catalog all magic values with extraction recommendations
   - Group related constants for efficient refactoring

4. **Lint Rule Compliance**
