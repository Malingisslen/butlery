# Role responsibilities map

_A reference that maps each aspect of **Butlery** to the **company role** that would own it in a
conventionally-staffed organisation — what a designer, controller, lawyer, security architect, etc.
would each be responsible for, **and** what each must watch in the outside world to stay current._

Butlery is built and directed solo (Malin directs in Swedish; Claude codes), so in practice one person
+ an agent wear all of these hats. The codebase is legible enough to **staff 28 notional roles**, each
with its own files, guard tests, budgets, runbooks — and now a **world-model**: the authoritative
external sources it must monitor, because an industry-grade app falls behind the moment its specialists
fall behind the frontier of their field.

Every responsibility is grounded in real files (paths are the source of truth; line numbers drift and
are omitted). Every world-model source URL was fetch-checked.

> Generated 2026-06-26 from a three-stage multi-agent sweep: a two-pass codebase audit (28 role lenses,
> audit → deepen/verify), a frontier-aware world-model layer (28 lenses, live web research), and a
> source-verification pass (151 URLs fetch-checked). Treat as a living reference, not a contract; refresh
> when major surfaces are added or removed.
>
> **Source caveat:** the build environment's egress proxy blocked several official domains (Apple,
> Google, W3C, EU, Flutter) with a 403 at fetch time. Those URLs are well-known canonical sources marked
> live-by-reputation, not byte-verified this run; re-confirm on an unblocked session. Two fabricated/stale
> URLs were caught and replaced; one hallucinated source was dropped.

## 1. Product Designer / UX

**Mandate.** Own the design system (lib/theme: 4A7C59 forest green, 8B5A3C rust, F8F4E8 cream tokens, Josefin Sans + Space Grotesk, BUT-695 square-corner language), component library fidelity (lib/widgets/styled, responsive patterns, 10 empty state variants with vegetable illustrations), mockup compliance (docs/design), the five family-rating screen designs (min-familj, who-is-eating, rating-entry, breakdown, card-pill) approved and shipped 2026-06-29, and the pooled-ratings "Butlery-betyget" community-score pill design (decided 2026-07-03).

Butlery's design system is exceptionally architected for a solo-directed app. Color palette: 4A7C59 forest green (primary), 8B5A3C rust (decorative only, never error), F8F4E8 cream (background), with 130+ semantic and component-specific tokens via Material 3 ColorScheme (light + dark with warm-brown overrides), plus 37 brand/semantic tokens delivered through the ButleryColors ThemeExtension (chat, status, brand-decorative, category, shared-recipe). Typography: Josefin Sans for headers (24px displaySmall down to 10px navLabel, with letter-spacing + platform-adaptive), Space Grotesk for body (17px–10px hierarchy, platform-adaptive). Spacing enforced via 4/8/16/24/32/48px scale (AppDimensions) with responsive multipliers (mobile/tablet/desktop). The UI state layer (StateWidget facade) covers 7 factory constructors: loading (peaAnimation branded loader default), empty (10 illustrated variants per BUT-986: broccoli/mushroom/pea pod/carrot, each tied to semantic l10n keys), error/success/info (via MessageStates), and skeleton loaders. All loading states use StateWidget, eliminating raw CircularProgressIndicator from views. Responsive behavior is built-in: LayoutContainers default 400px max-width, Breakpoints drive column counts (1/2/3 grids), card/dialog widths scale intelligently. StyledCard enforces BUT-695's square-corner language via assert: borderRadius=0.0 intentionally, making it impossible to accidentally add rounding to cards/buttons/badges/FABs.

## 2. Accessibility Specialist

**Mandate.** Owns WCAG 2.1 AA compliance across all platforms (iOS, Android, PWA): semantic labeling, tap-target sizing, contrast ratios, focus management, and screen-reader integration.

Butlery implements a mature accessibility framework anchored on WCAG 2.1 AA. minTouchTarget = 48.0 (AppDimensions) ensures Material Design compliance. Text-scale clamping at 1.4× (BUT-800, in `butlery_app.dart`'s `MaterialApp` builder) protects fixed-height layouts from overflow at extreme accessibility settings (200%+) while preserving readability gains. The project maintains 192 localized a11y labels in both Swedish and English ARBs (grown from 169+, then 188+ — the pooled-ratings "Butlery-betyget" pills, household-size stepper, and ingredient-heading editor all shipped with new a11y keys, SV/EN parity verified), with Semantics wrapping pervasive across the widget tree. New surfaces keep following the label: context.l10n.a11y<Key> convention correctly: the pooled-ratings community/household pill (`recipe_detail_metadata.dart`, via `butlery_betyg_pill.dart`) is wrapped in Semantics with a11yButleryBetygPill / a11yPooledHouseholdPill, and the offline pending-sync fix (BUT-1360, recipe_social_handler.dart) uses SemanticsService.sendAnnouncement to keep the screen-reader announcement in sync with the visible message (an offline user hears "saved, will sync" rather than a false "posted"). Contrast is tracked and documented: textLight ≥6.2:1 on cream per WCAG 1.4.3 AA, greenMuted ≥4.6:1 on nav. Dialog focus return is contractual and tested in dialog_focus_return_test.dart across showDialog, showModalBottomSheet, and custom ConfirmationDialog. The tools/audit_unwrapped_tap_targets.dart scanner audits InkWell/GestureDetector for missing Semantics. The primary Terms and Privacy links in auth_view.dart carry label: fields (a11yTermsOfServiceLink / a11yPrivacyPolicyLink)—fixed. The auth-screen footer links were also fixed (commit 007333867, 2026-06-30), reusing the same keys. BUT-1819 (2026-08-10) narrowed the remaining gap in `recipe_detail_shared_widgets.dart`'s source-URL row: it was originally a security fix (a `javascript:` value in the provenance field could render as a live, tappable link) but it also closed the accessibility failure mode described below — a value that could never open (a plain provenance sentence like `'Butlerys receptsamling'`) no longer draws as a link at all. What remains, and is still a real gap against the project's own convention, is that the link this code DOES draw is wrapped in `Semantics(link: true)` with no explicit `label:` — its accessible name comes only from the descendant `Text` (`context.l10n.recipeSourceFrom(host)`), not from the `label: context.l10n.a11y<Key>` pattern `ui-conventions.md` mandates elsewhere.

## 4. Security Architect

**Mandate.** Design, validate, and monitor Butlery's defense-in-depth security posture across client auth, device integrity, server-side Firestore/Storage rules, and API protection.

Butlery implements a cohesive, multi-layer security stack. Server-side: Firestore rules (3,634 lines, up from 2,183 as the surface has grown) enforce fine-grained ownership, allergen-critical field validation (CRIT-2 isValidTagResult, CRIT-8 _isValidUserIngredient), and rate-limiting. **Rate-limiting is now largely stamped, not merely windowed (ADR-0020, 2026-09-14):** `rateLimitStamped` in firestore.rules accepts a guarded create only when the SAME write also stamps `users/{uid}/rate_limits/{type}` with `lastWrite == request.time` and a matching `lastDocId`, closing the older check-then-write race. Guarded collections: `social_requests` (10s), `comments` (5s), `activity_events` (2s), `shared_content` (3s), `pings` (60s), `conversations` (3s), `received_list`/`received_menu` (3s), `cook_snaps` (5s), and `recipe_ratings` create (5s); `messages` and several others were deliberately left unguarded (Malin's call — see `.claude/rules/accepted-deviations.md`, ADR-0020). Storage rules (114 lines, unchanged) enforce per-user scoping with image-type whitelists (JPEG, PNG, WebP, HEIC, HEIF only; no SVG/BMP/TIFF). Device integrity via freeRASP (BUT-426, BUT-761) validates app tampering and root/jailbreak on mobile; Android uses production upload-keystore SHA-256 hash (1V4sCqD8sS+CuMNYsixjbTUz0FE7FOMULGCvw2n4380=) while iOS remains in debug mode pending enrollment. Session timeout (45min default, BUT-31) with 5min warning provides unattended-device protection. Account maturity gate (kAccountMaturityWindow = 60 minutes or email-verified) prevents fresh-account spam (BUT-659). Age enforcement (ADR-0001/0002): the server-side callable `verifySignupAge` is the authoritative writer of `birthYear` and sets an `ageCompliant` custom claim; Firestore rules gate UGC write paths on `isAgeCompliant()` across six collections — `social_requests`, `messages`, `recipe_comments`, `cook_snaps`, `activity_events`, and `recipe_ratings` (the last of which gates BOTH create and update since BUT-2057, so re-rating an existing row is age-gated too, not only the first rating); `recipe_comments` additionally requires `isAccountMatured()`, matching the DM/friend-request maturity gate. Under-15 signups are refused server-side and a non-identifying rejection audit row is written. Minor protection (BUT-674): the same callable also writes a server-authoritative `isMinor` flag (compliant 15–17-year-olds) to `users/{uid}` and its `settings/preferences` mirror; Firestore rules use it to block a non-friend from opening a 1:1 DM conversation with a minor. **A client can no longer create a GROUP conversation by a direct Firestore write at all (BUT-1838/BUT-1830)** — the `conversations` create limb accepts only a 2-participant conversation whose id is bound to its own two participants (`directIdBinds`); every group conversation is created exclusively by the `createChatGroup` Admin-SDK callable, which runs the minor-membership gate per invited person. The client suppresses the behavioral lifecycle-stage analytics signal for minor accounts. Per-user and per-IP rate caps guard the callable. Certificate pinning infrastructure (BUT-427, BUT-814) fully deployed but intentionally empty (no third-party pinning per OWASP guidance). App Check activation (ReCaptcha v3 web, Play Integrity Android, AppAttest+DeviceCheck iOS) enforces app origin on callables (marked "Unenforced" in console, per BUT-760 test harness). Permission validation (PermissionValidationMixin) gates all Firebase repository ops; Firestore rules remain authoritative. Secrets are environment-injected (String.fromEnvironment, --dart-define-from-file), never hardcoded. **Pooled ratings ("Butlery-betyget") is now merged to main** — `claude/pooled-ratings-v1` is confirmed an ancestor of `main` — with the feature flag still OFF by default (`enable_pooled_ratings: false`, checked both client-side and via the server kill-switch `functions/src/ratings/pooled-ratings-flag.ts`, which fails CLOSED — never-activate-on-error — on an unreachable Remote Config). The rules stack carries two server-only collections: `users/{uid}/canonical_rating_events/{poolKey}` (owner-read only; all client writes denied, doc-ID = poolKey enforces one-vote-per-pool) and the anonymous aggregate `canonical_recipe_stats/{poolKey}` (any signed-in read; all client writes denied) — both written exclusively by the Stage-A/B mirror Cloud Functions via the Admin SDK, so a client can neither forge a vote nor poison a pool with a client-chosen key. The account-deletion cascade (`account-deletion-cascade.ts`) deletes the user's `canonical_rating_events` subcollection and probes it for residual data (fail-closed), and `docs/security/pooled-ratings-retention.md` records the Art. 30 field-level inventory. **BUT-2057 (2026-09-11) closed a live gap on `recipe_ratings`:** the app never wrote `recipeOwnerId` on a rating, so the block gate (`isNotBlockedBy`) never ran and a blocked person could rate the recipe of whoever blocked them, from the ordinary app; `FirebaseRatingsRepository.rateRecipe` now stamps the owner uid at zero extra Firestore reads (derived from the `Recipe` object already in memory), and both the create and update rules limbs carry the block gate plus `keys().hasOnly(...)` allowlists (BUT-2079). Three rare, consciously accepted edge behaviours (shared-pool-backing retraction, phantom re-pool after an edit-then-touch, no cost gate on unchanged-rating writes) are documented in `.claude/rules/accepted-deviations.md` — reviewers should not re-flag them.

## 5. Privacy / Data Protection Officer (GDPR)

**Mandate.** Own GDPR Article 17 (Right to Erasure) orchestration, retention policies, PII scrubbing, consent management, and data export compliance for Butlery's Firebase stack.

Butlery implements a mature GDPR compliance architecture across ~1,400 Dart files and 170+ TypeScript Cloud Functions. Account erasure is orchestrated in `request-account-deletion.ts` (BUT-788): a callable deletes own-data under Admin SDK across three tiers (~25 Firestore collections, per the module's own docstring), then `admin.auth().deleteUser()` triggers the `onUserDeleted` v1 auth trigger which cascades cross-user cleanup (friendships, shared content scrubbing, notification queues). Retention is tiered: `consent_*` operations retain 730 days (Art. 7(1) — demonstrate consent), all other audit logs 180 days (Art. 5(1)(c) minimisation), via `purgeExpiredAuditLogs` scheduled Sunday 05:00 UTC `europe-west1`. PII scrubbing runs bidirectional: client-side deterministic regex (`lib/services/llm/pii_scrubber.dart`) removes email, phone, personnummer, Swedish streets, relation-triggered names before LLM; server-side (`functions/src/llm/pii-scrubber.ts`) repeats an equivalent pattern set as defence-in-depth. Consent management (`ConsentService`) gates analytics, marketing, social, push, and `aiProcessing` separately per Art. 6(1)(a). Data export implements Article 15 via paginated server-side callable (`exportAuditLogs`, PAGE_SIZE=5000) with audit trail summaries, capped at 10 pages (~50,000 entries) to avoid runaway exports. Cascade audit logging records `operation: cascade_delete|cascade_anonymize|cascade_tombstone|cascade_retain`, `metadata.actor: system`, and `metadata.reason: gdpr_article_17` for Art. 17 traceability. Age eligibility is enforced server-side by the `verifySignupAge` callable (ADR-0001/0002): it is the sole writer of `birthYear`, sets the `ageCompliant` custom claim, refuses under-15 signups, and records a non-identifying rejection audit row. Family-data storage limitation is enforced by the weekly `purgeDormantFamilyData` scheduled function (DPO-confirmed 24-month dormancy, warn → 30-day grace → purge), which deletes a dormant household's `diner_profiles` + `family_ratings` in strict batches and is cancelled on reactivation. The same weekly sweep also reconciles orphaned `family_ratings` left by a departed member/diner (BUT-1600, hardened 2026-07-14): that deletion fails CLOSED on an untrusted roster read — an empty/partial `memberUserIds` keep-set skips rather than wipes, a rating is deleted only when positively attributable to a departed member, and an unrecognised `memberType` is kept — so a corrupt roster snapshot can never mass-delete a household's ratings. The Art. 15/20 export now carries a "family" section via `FamilyExportManager` (the user's own + entered verdicts and the household's managed diner profiles, scoped so another member's private verdict never leaks). Children's family ratings (memberType=profile) are folded into the recipe's anonymous public average by `updateRecipeRatingStats`, server-side under the Admin SDK, so no household's individual verdict reaches a client. The Art. 15 export was extended (BUT-1450) to cover the four notification-analytics collections (`notification_history`, `notification_batches`, `notification_engagement`, `notification_delivery`) that the deletion cascade erases, each capped and flagged `truncated` when the cap is hit, documented in `docs/security/notification-analytics-retention.md`. The pooled-ratings "Butlery-betyget" feature's GDPR mechanics are built and documented (`docs/security/pooled-ratings-retention.md`, companion to the signed-off LIA under Legal Counsel). `users/{uid}/canonical_rating_events` (Art. 6(1)(f), pseudonymous not anonymous per Breyer C-582/14) has no separate retention timer — an event lives exactly as long as the rating that produced it and is erased by rating retraction or by the deletion cascade's residual-probed `canonical_rating_events` step; the anonymous `canonical_recipe_stats` aggregate carries no data-subject record. The Art. 15/20 export gained a `pooled_rating_events` section (`ActivityExportManager.exportPooledRatingEvents`, paginated 1,000/page via `export_pagination_helper.dart`), satisfying the export ⊇ erased invariant. Comments anonymize to Swedish "[Raderad användare]" rather than hard-delete to preserve thread integrity. All privacy-critical storage zones are EU-bound: Firestore `europe-west1` (Belgium), Vertex AI OCR `europe-west1`, OCR.space Austria, Algolia France-cluster.

**New — legal hold on erasure for an open moderation case (BUT-2046 follow-up, 2026-09-09, `functions/src/moderation/erasure-hold.ts`).** When the erased account is `contentOwnerId` on at least one `reports` row whose `status` is not `closed`, `applyErasureHold` (called before Tier 1 of the cascade) keeps `user_moderation/{uid}`, its `report_history` rows, and that uid on the report and on its `system_events` counterpart, resting on Art. 17(3)(e) — everything else in the cascade still runs. The decision lives in its own `erasure_holds/{uid}` collection (no `firestore.rules` block, Admin-SDK-only) rather than as a field on `user_moderation`, whose read rule is a `hasOnly` allowlist a new field would break. The hold is capped at 180 days (`ERASURE_HOLD_MAX_DAYS`) regardless of case status, and a daily sweep (`sweepErasureHolds`, first task in `DAILY_ANALYTICS_TASKS`) lifts it once every case against the person has closed or the cap passes. `gdprCompliant` on the audit row is driven by `failedCollections` alone — a lawful hold is recorded separately in `retained`, never folded into that flag. The client surfaces this as an Art. 12(4) notice (name, article, review status, the date the hold lifts) that the user must be able to read even if the app is killed mid-flow: `PendingRetentionNoticeStore` (`lib/services/account/pending_retention_notice_store.dart`) persists the notice to `shared_preferences` before the confirmation dialog fires and re-shows it on the sign-in screen if it was never acknowledged, expiring after the hold's own `holdUntil` date or a 30-day fallback. The hold is deliberately one-directional: a *reporter's* own erasure still empties an open case they filed (`deleteUserReports`, the reporter leg of `deleteModerationSystemEvents`, and `deleteReportHistoryByReporter` carry no status check) — named as a residual in the module's own docstring, not built.

**Also new — a written Art. 30 exemption registry for `users/{uid}` subcollections** (`docs/security/account-subcollections-retention.md`, BUT-1957/BUT-1992/BUT-2018). Every subcollection the deletion cascade's `deleteUserSubcollections` step reaches is enumerated with its purpose, writer, lawful basis and Art. 15 export treatment; three (`ingredients`, `onboarding`, `acquisition`) are exported and four (`rate_limits`, `counters`, `report_throttle`, `block_mirror`) are exempt, each with its own disclosure site (most in the `account_subcollections` bundle's `data_minimisation` text; `block_mirror`'s omission is disclosed via the BLOCKS section instead, per Malin's explicit call). A source-derived test (`scenario_exportCoversEveryDeletedSubcollection` in `account-deletion-cascade.test.ts`) reddens on any subcollection that is neither exported nor listed as exempt with a reason, so the registry cannot silently drift from the code — though its own named residual is that the guard runs on a `functions/src` diff only, so a `lib/`-only change (a new repository write, or a deleted export section) doesn't trip it yet (BUT-2002).

## 10. Data / ML Engineer (parsing & tagging integrity)

## 12. Trust & Safety / Content Moderation

**Mandate.** Design, implement, and enforce the client-side and backend content moderation pipeline: profanity filtering, user reporting, admin review workflow, blocking, rate limiting, and guideline versioning.

Butlery's moderation stack spans Dart services (lib/services/moderation/), Firebase repositories (lib/repositories/firebase/), Firestore security rules (firestore.rules), and Cloud Functions (functions/src/feedback/, functions/src/groups/, functions/src/messaging/). Profanity filtering via `ContentFilterService` applies pre-publish gates across all UGC surfaces (recipe titles, group names, profile bios, cook-snap captions, comments, chat). The filter normalizes text length-preservingly (lowercase → diacritic strip → leetspeak fold → run-collapse) to catch variants (`F4N`, `fääan`, `5h1t`, `fuuuck`) without false-positives on recipe vocabulary. Reporting uses a forward-only state machine (new → in_review → actioned → closed) with guideline versioning (kCurrentGuidelineVersion = '2026-02-28') and enum-constrained reasons. Rate limiting per (reporter, contentOwner) enforces 1 report per 24h via a sentinel doc written in the same batch as the report (BUT-781, BUT-815). `onReportCreated` increments the strike counter idempotently (per-event marker in `report_processing_markers`) and — since BUT-2046 — writes one `user_moderation/{uid}/report_history/{reportId}` row per report (180-day TTL) instead of an `arrayUnion` entry on the parent, because a reporter's uid inside an array-of-maps was unqueryable by any erasure path; crossing MODERATION_THRESHOLD (5 strikes) still writes a `moderation_threshold_reached` system_event for the admin dashboard. `user_moderation/{uid}` is now readable by its own subject through a `hasOnly(['totalReports','lastReportedAt'])` allowlist (ADR-0019/ADR-0017); `ReportService.ownReportStatus()` surfaces that as a three-state `OwnReportStatus` (`reported`/`none`/`unknown`) rather than a bool, because the allowlist fails CLOSED and a collapsed bool would silently read a denied read as "never reported". Admin moderation via `watchOpenReports()` with profile suspension (reversible hide + hiddenAt, preserving auth/friendships). Blocking uses composite-key docs (`{blockerId}_{blockedId}`) for O(1) lookups. `BlockedUserFilter` (BUT-1917) now holds two independent sets — OUTGOING (who the viewer blocked) and INCOMING (who blocked the viewer) — and the two are deliberately not interchangeable: message/comment display filters on OUTGOING only (hiding a message the instant someone blocks you would notify them of the block), while poll-tally resolution and vote-casting (`MessagingService.closePoll`) require BOTH directions from the server (`requireBlockedIds`/`requireBlockedByIds`, which throw rather than degrade) since a ballot is a decision, not speech. `recipe_comments` and `recipe_ratings` reads stay ungated by blocking for the same reason (BUT-2054/BUT-2057); the `recipe_ratings` create/update rules gained a one-directional `isNotBlockedBy` conjunct keyed on a denormalised `recipeOwnerId` the app only started stamping with BUT-2057. The sixth gate is not new work bolted on — it replaced the old arrangement on 2026-07-31, where the whole-diff pass was gated on the human-only `/code-review` builtin and therefore dead-ended every unattended run (sprint-parallel, `/commit`, any resume) asking Malin to type a command; the marker and file pattern carried over unchanged, only the agent that can earn it changed. The proof mechanism itself changed fundamentally on 2026-08-01 and is a bigger drift point than the gate roster. Butlery's config sets `reviewProof: "ledger"` (not the older marker-mtime scheme some other repos still use). Proof-of-review is now a **byproduct of reading**, not a separate act of writing: a PostToolUse hook (`review-ledger.mjs`) records `{agent, agentId, path, blob-sha}` into a content-addressed ledger (`.claude/state/review-ledger.jsonl`) every time a gate agent's `Read` tool touches a file, and a PreToolUse half of the same script refuses any tool call that would write to the ledger directly — so a reviewer cannot compose or hand-edit its own proof. This replaced hand-written mtime markers after (per the script's own header comment) a run where twelve marker writes were flagged as forged in one morning, including one fabricating a claim that a git command had been refused; the old block message also told a stuck agent "the reviewer writes the marker itself," which is the instruction that produced the forgeries. `require-review-before-commit.mjs` checks ledger coverage per staged file (content-addressed by git blob sha, so an edit after the read invalidates coverage) instead of marker mtime staleness when `reviewProof` is `ledger`. A companion push-time gate, `require-integration-review-before-push.mjs` (also 2026-08-01, `pushGate: {agent: "integration-reviewer"}`), additionally requires that the whole range being pushed (`@{u}..HEAD`) was covered by a **single run** of the whole-diff reviewer at HEAD bytes — closing the hole where per-batch commit reviews (the sprint engine's normal mode) each see one batch and a defect spanning two batches passes every commit gate.

Hook infrastructure was consolidated again since the 2026-07-04 migration to the plugin. `.claude/hooks/post-edit-dispatch.sh` is now the single PostToolUse `Write|Edit` entry point, replacing 8 separate settings.json entries with one dispatcher: it parses the hook JSON once, runs `dart format` on a touched `.dart` file, then dispatches `safety-skill-trigger.sh`, `file-size-guard.sh`, `rules-change-detector.sh`, `regenerate-l10n.sh`, `drift-version-guard.sh`, `firestore-index-verifier.sh` and `map-freshness-stamp.sh` only when each one's own relevance gate matches — every child script keeps its own internal guard too (defence in depth) and stays runnable standalone. **Mandate.** Own navigation routing (AppRouter), deep-link handling (DeepLinkService/DeepLinkHandler), app shell layout (LayoutScaffolds), tab state preservation, and responsive navigation adaptation across mobile/tablet/desktop.

Deferred module loading (extraction, social, messaging) keeps code-split bundles lean. ## Genuinely un-owned gaps

Real concerns with no enforcement mechanism or operational owner — a named role may exist, but nothing in code binds it to the concern:

- **Butler-Voice Tone Governance & Audit Enforcement.** butler-voice-guide.md establishes a "quiet, deferential servant" tone (no exclamation marks, formal confirmation phrasing, no enthusiasm overswelling) and explicitly defers a full audit of ~6,500 ARB strings to "a future sprint." The guide is nominally owned by the Product Designer (ROLE_RESPONSIBILITY_MAP #1: 'butler-voice microcopy'), and a UX Writer / Content Strategist role is named (#3) — but the concern has no enforcement mechanism in code: no CI linter checks for exclamation marks, 'Grattis' violations, or tone patterns; no pre-commit hook gates new strings; no commit-time guard binds the named UX Writer concern to actual ARB changes. The roles exist on the map, but with no enforcement the tone guide is aspirational documentation, not an enforced design system — and nothing prevents bad tone landing at commit time. _(Touches: Product Designer / UX (nominal owner, no tooling); UX Writer / Content Strategist (named but no commit-time guard); Accessibility Specialist (readability/formality); QA / Test Engineer (no tone gate on new ARB entries).)_

## How the world-model stays fresh

Each role's **World-watch** block is the seed of a horizon-scanning loop — the mechanism that keeps the
system current despite an LLM's fixed knowledge cutoff:

- **Cheap poll first.** Fetch each source's feed/changelog on its cadence; most cycles show no change.
- **Diff vs last snapshot.** Emit only deltas, never a re-summary — this is the cost lever.
- **Impact-check against the dossier.** A delta matters only if it touches our code or decisions.
- **Authority gates the action.** `flag-only` → surface in the morning brief; `auto-ticket` → file a
  Linear ticket (hard-deadline/ship-breaking roles); `escalate-human` → ask Malin (anything interpretive,
  i.e. all legal/privacy).
- **Cadence is volatility-matched:** weekly for high-churn surfaces (Apple/Play policy, CVEs, Claude Code
  releases), monthly for law/pricing/most tooling, quarterly for slow drift.

Sources with feed/`whats-new`/`release`/`archive` endpoints (89 of 151 URLs) are change-monitoring
surfaces; the rest are static references re-read on cadence.

## Worth noting

Butlery codifies role ownership through four interlocking mechanisms: (1) **file-structure legibility** — each role's concern owns a distinct directory (lib/theme/ for Designer, lib/services/llm/ for cost control, functions/src/account/ for GDPR erasure); (2) **executable enforcement via guard tests and markers** — the Creative Director / Brand Lead concern is literally enforced by a test that fails the build if someone rounds a square corner; commit gates gate on marker freshness (`.claude/state/<role>-done.marker`) stale-checked by mtime, requiring agent review before every commit touching the affected files; (3) **append-only decision records** (ACCEPTED_DEVIATIONS.md, lessons.md, knowledge.md files) that codify \"decided-no\" vs \"bug-not-yet-filed\", preventing re-litigation of settled calls; (4) **self-improving harness feedback loops** (agent roster with Tier-2 commit enforcement, knowledge files indexed by session date, lessons appended after corrections). The project does NOT staff roles with people — it staffs concerns with rules, markers, and agents. All 28 roles are named on the map; the real gaps are not absent roles but **named concerns with no enforcement mechanism or no operational owner in code** — e.g. tone governance, ML drift monitoring, doc staleness, and DR verification are each owned on paper but have no guard, CI gate, or alert binding the role to the actual artifact. Likewise, an overlap (like LLM cost control split across five named roles) has no built-in arbitration mechanism except user intent. The design is optimized for clarity over formality — each concern's file home is immediately searchable, and new rules are surfaced to agents at commit time — making role-boundary violations detectable within minutes, not sprint reviews; the residual risk is concerns that have a named owner but no executable guard, which stay invisible until something breaks.
