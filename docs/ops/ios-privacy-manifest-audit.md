## Corrections on restore (2026-08-25) — this document contradicted the file it documents

Three claims below were measured against `ios/Runner/PrivacyInfo.xcprivacy` and are wrong.
They are corrected in place further down; listed together here so nothing is filed from the
stale version:

1. **"We intentionally do not declare DiskSpace / SystemBootTime"** — the manifest declares
   **both**: `NSPrivacyAccessedAPICategoryDiskSpace` (`E174.1`, Firestore cache + Crashlytics)
   and `NSPrivacyAccessedAPICategorySystemBootTime` (`35F9.1`, Performance Monitoring).
2. **FileTimestamp reason `C617.1` only** — the manifest carries **two** reasons,
   `C617.1` *and* `3B52.1`. The companion doc `ios-third-party-privacy-manifests.md` cites only
   `3B52.1`; each doc had half the answer.
3. **The collected-data-types summary lists 9 rows** — the manifest has **10**. The missing row
   is `NSPrivacyCollectedDataTypeHealthAndFitness` (allergen + dietary preferences, BUT-811 /
   HIGH-LEGAL7), which landed after this audit was written. That row is also why
   `play-data-safety-runbook.md` §2.3 is now an open question rather than a flat "No".

This document is the evidence paper trail for the App Store reviewer. It
answers the question: *for every SDK we link on iOS, does it ship its own
privacy manifest, and if not, did we declare its required-reason APIs on
its behalf?*

## Methodology

1. Enumerate every direct dependency in `pubspec.yaml` that has an iOS
   native component (plugins, not pure-Dart packages).
2. For each, determine whether the pod ships a bundled
   `PrivacyInfo.xcprivacy` (Xcode auto-merges those; we must NOT duplicate
   their reasons).
3. For pods WITHOUT a bundled manifest, declare required-reason APIs on
   their behalf in `ios/Runner/PrivacyInfo.xcprivacy`.
4. Declare all data-type collection in `NSPrivacyCollectedDataTypes`
   (first- and third-party combined).

**`ios/Podfile.lock` is generated by `pod install` on a Mac**, which has
not been run on this Windows workstation. This audit is based on
`pubspec.yaml` + each plugin's public source repository. A follow-up
verification pass on macOS should run `grep -r PrivacyInfo.xcprivacy
ios/Pods/` and confirm the "ships own manifest" column below before
App Store submission.

## NSPrivacyAccessedAPITypes — declarations we carry

We declare the minimum set of required-reason categories that cover
first-party code and the few pods that (as of their current published
source) do not ship their own manifest:

**(re-measured 2026-08-25 against the manifest — the previous version of this table listed two
categories and explicitly disclaimed two more that the manifest in fact declares.)**

| Category | Reason code(s) | Covers |
|---|---|---|
| `NSPrivacyAccessedAPICategoryUserDefaults` | `CA92.1` | freerasp internal state flags, flutter_inappwebview cookie/session store, image_cropper session flags |
| `NSPrivacyAccessedAPICategoryFileTimestamp` | `C617.1` **and** `3B52.1` | `C617.1` — image_picker / image_cropper read EXIF + creation timestamps surfaced to the user. `3B52.1` — cached_network_image, flutter_image_compress and sqlcipher read mtimes for app-internal cache LRU eviction; never leaves the device |
| `NSPrivacyAccessedAPICategoryDiskSpace` | `E174.1` | Firestore's on-device persistence cache (LRU GC) and Crashlytics check free space before writing. Firebase ships its own manifest covering this; declared at app level so the merged App Store privacy report enumerates the reason explicitly |
| `NSPrivacyAccessedAPICategorySystemBootTime` | `35F9.1` | Firebase Performance Monitoring trace durations and Analytics session timing derive from boot-relative timestamps. On-device until analytics consent is given (BUT-412) |

We intentionally do **not** declare:

- `NSPrivacyAccessedAPICategoryActiveKeyboards` — not used.

## NSPrivacyTracking

`false`. Butlery:

- Does not collect IDFA.
- Does not pass user data to third-party ad networks.
- Gates Firebase Analytics behind an explicit consent toggle (BUT-412 in
  the previous launch-readiness sprint).
- `NSPrivacyTrackingDomains` is empty.

## Follow-up — verification on macOS before submission

1. Run `pod install` in `ios/` on the build machine.
2. `grep -l PrivacyInfo.xcprivacy ios/Pods/**/` — confirm every pod in the
   "Ships own manifest? = Y" column above actually bundles one.
3. For any pod marked `N *(verify)*` that DOES bundle a manifest upstream
   (versions may have moved since this audit), flip its row to Y.
4. For any pod that still has no manifest, confirm our declared reasons
   cover its actual API usage, or add missing categories.
5. Build archive, upload to App Store Connect, confirm the privacy report
   in App Store Connect matches this doc.
